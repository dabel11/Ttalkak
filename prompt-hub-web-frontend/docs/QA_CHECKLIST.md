# TTALKAK Frontend QA Checklist

이 문서는 최신 웹 프론트엔드와 Spring Boot 백엔드 연동 상태를 확인하기 위한 수동 QA 목록입니다.

## 실행 준비

- Backend: `http://localhost:8080`
- Frontend: `http://127.0.0.1:4173`
- Browser DevTools Network 탭에서 `/api` 요청이 Spring Boot로 나가는지 확인합니다.
- 기본 통합/시연 모드에서는 백엔드가 꺼져 있으면 데모 데이터로 자동 fallback되지 않아야 합니다. 상단 상태 배지에는 `Backend 오류` 또는 서버 연결 실패 안내가 보여야 합니다.
- 개발자가 `window.TTALKAK_DEMO_FALLBACK_ENABLED = true`를 명시한 경우에만 데모 fallback을 허용합니다. 이때는 화면에서 데모 데이터임을 구분할 수 있어야 합니다.

## Home

- `GET /api/prompts` 응답의 `items` 또는 `content`가 그대로 렌더링되는지 확인합니다.
- 서버 응답의 `totalPages`, `totalElements` 기준으로 페이지네이션이 표시되는지 확인합니다.
- 서버 API 연결 상태에서는 프론트가 다시 `slice()` 페이지네이션을 적용하지 않는지 확인합니다.
- 검색어, 검색 범위, 정렬 선택은 서버 요청 파라미터로 전달되고 화면은 서버 결과를 그대로 표시하는지 확인합니다.
- 추천 해시태그, 카드 태그, 작성자 닉네임 클릭 시 Home 검색 결과로 자연스럽게 이동하는지 확인합니다.
- 카드 클릭 시 상세 모달이 열리고, 모달 바깥 클릭 또는 닫기 버튼으로 닫히는지 확인합니다.
- 신고 숨김은 계정별 상태로 적용되고 다른 계정으로 전환했을 때 섞이지 않는지 확인합니다.

## Auth

- 일반 로그인과 관리자 로그인 모두 실제 `/api/auth/login` 응답 토큰으로 동작해야 합니다.
- 로그인 성공 후 `ttalkak_access_token`이 저장되고, 인증 API 요청에 `Authorization: Bearer ...` 헤더가 붙는지 확인합니다.
- 401 응답 시 토큰이 정리되고 로그인 안내가 표시되는지 확인합니다.
- 403 응답 시 권한 없음 안내가 표시되는지 확인합니다.
- 백엔드 로그인 요청이 timeout 되어도 데모 관리자 세션으로 자동 진입하지 않아야 합니다.
- 회원탈퇴는 `DELETE /api/auth/withdraw`를 호출하고 성공 후 토큰과 로그인 상태가 초기화되는지 확인합니다.

## Make

- 프롬프트 개선은 Spring Boot `POST /api/prompts/improve`만 호출해야 합니다.
- 브라우저 Network 탭에 FastAPI `/query`, 포트 `8000`, RAG 서버 URL, AI provider endpoint로 직접 나가는 요청이 없어야 합니다.
- Make 진입 시 `GET /api/make/threads`, `GET /api/make/folders`가 정상 호출되는지 확인합니다.
- `ragStatus: "no_evidence"`인 경우 결과는 표시하되 RAG 근거 없이 기본 첨삭을 수행했다는 안내가 보여야 합니다.
- 기본 통합/시연 모드에서는 429, 500, 503, 504 상황에서 데모 첨삭 결과가 아니라 오류/재시도 안내가 표시되어야 합니다.
- 데모 fallback 플래그를 켠 개발 모드에서만 데모 첨삭 fallback 안내가 표시되는지 확인합니다.
- 새 폴더 생성, 스레드 이동, 같은 첫 입력 재전송이 서버 ID 기준으로 동작하고 임시 ID가 서버 PATCH에 전달되지 않는지 확인합니다.

## Share

- 로그아웃 상태에서 Share 진입 또는 공유 시 로그인 안내가 표시되는지 확인합니다.
- 제목과 프롬프트가 있을 때 공유가 가능하고, 해시태그는 선택 사항으로 동작하는지 확인합니다.
- 해시태그 검색 결과가 없으면 새 태그 추가 버튼이 표시되는지 확인합니다.
- 해시태그 제안 값에 따옴표, `<script>`, `<img onerror=...>` 같은 값이 들어와도 DOM 구조가 깨지지 않고 일반 텍스트로 표시되는지 확인합니다.
- 공유 성공 후 Home 최신 정렬 또는 검색에서 방금 공유한 프롬프트가 보이는지 확인합니다.

## My Page

- 로그아웃 상태에서는 My page 메뉴가 보이지 않아야 합니다.
- 신규 로그인 사용자의 My page는 기본적으로 비어 있고, 데모 데이터와 서버 데이터가 섞이지 않아야 합니다.
- 내 보관함, 내가 만든 프롬프트, 댓글 관리, 신고 내역이 서버 응답과 최근 로컬 활동을 함께 반영하는지 확인합니다.
- 수정 요청됨 상태의 내 게시물 신고 내역에만 `수정하기` 버튼이 표시되는지 확인합니다.
- `수정하기` 클릭 후 수정 모달에서 관리자 수정 요청 사유가 함께 표시되고, 저장 후 My page 목록이 갱신되는지 확인합니다.

## Prompt Detail And Comments

- 상세 모달에서 왼쪽 프롬프트와 오른쪽 댓글 영역이 분리되어 보이는지 확인합니다.
- 댓글/답글 작성, 수정, 삭제, 좋아요, 신고가 권한에 맞게 동작하는지 확인합니다.
- 로그인하지 않은 사용자는 저장, 좋아요, 댓글, 공유, 신고, 폴더 관리 같은 로그인 필요 기능이 막히는지 확인합니다.
- 삭제된 댓글은 원문 대신 삭제 안내가 표시되고 답글 구조는 유지되는지 확인합니다.

## Admin

- 관리자 권한 계정으로 로그인했을 때만 Admin 메뉴가 보여야 합니다.
- 관리자 계정에서는 운영 화면 중심으로 접근하고, 일반 사용자용 My page/Share 메뉴가 숨겨지는지 확인합니다.
- 신고 관리는 전체, 프롬프트, 댓글 탭으로 구분되고 각 신고 유형별 액션이 명확히 보이는지 확인합니다.
- 신고 상태 변경, 게시물 숨김/해제, 댓글 숨김/해제/삭제, 태그 승인/반려, 사용자 차단/해제가 서버 실패 시 로컬 상태를 잘못 변경하지 않는지 확인합니다.
- 사용자 활동 검색은 닉네임 부분 검색 결과 목록을 먼저 보여주고, 관리자가 선택한 `memberId` 기준으로 상세 활동을 조회해야 합니다.
- 작성자 닉네임 클릭 시 `author.id` 기준으로 사용자 활동 화면이 열리는지 확인합니다.
- 감사 로그에는 신고 상태 변경, 댓글 조치, 작성자 수정 요청 생성/수정/상태 변경이 식별 가능한 action과 detail로 표시되는지 확인합니다.

## XSS And Escaping

- 프롬프트 제목, 프롬프트 내용, 댓글 내용, 태그명, 닉네임, 신고 사유, 관리자 메모, 수정 요청 사유, 검색어에 `<script>alert(1)</script>`를 넣어도 스크립트가 실행되지 않아야 합니다.
- HTML 속성에 들어가는 동적 값은 `escapeAttr()` 또는 DOM dataset 기준으로 안전하게 처리되어야 합니다.
- URL query/path에 들어가는 값은 `encodeURIComponent` 등 URL 문맥에 맞게 인코딩되어야 합니다.

## Known Partial Areas

- 웹사이트 P0-1 구조 개선은 상당 부분 진행됐지만, `app.js`에는 아직 일부 라우팅, 상태 연결, 이벤트 orchestration 로직이 남아 있습니다. 기능 변경 없이 단계적으로 더 얇게 줄이는 후속 작업이 가능합니다.
- Chrome Extension의 운영 서버 검증은 운영 Backend URL과 Extension ID가 확정된 뒤 진행해야 합니다.
