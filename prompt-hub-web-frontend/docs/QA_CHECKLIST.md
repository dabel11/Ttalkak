# TTALKAK Frontend QA Checklist

이 문서는 `jaewon7025/web-demo-preview` 브랜치를 백엔드와 함께 실행할 때 확인할 수동 테스트 목록입니다.

## 실행 준비

- Backend: `http://localhost:8080`
- Frontend: `http://127.0.0.1:4173`
- Browser DevTools Network 탭에서 `localhost:8080` 또는 `/api` 요청을 확인합니다.
- 백엔드가 꺼져 있으면 프론트는 데모 데이터로 fallback되며, 상단 상태 배지에 `Demo data 표시 중`이 보여야 합니다.
- 백엔드가 켜져 있으면 상단 상태 배지에 `Backend 연결됨`이 보여야 합니다.

## Home

- `GET /api/prompts`가 200으로 응답하는지 확인합니다.
- `GET /api/tags/popular`가 200으로 응답하는지 확인합니다.
- 카드 작성자가 `[object Object]`가 아니라 닉네임으로 표시되는지 확인합니다.
- 추천 해시태그가 검토 완료 태그 기준으로 표시되는지 확인합니다.
- 검색 범위 드롭다운 `전체 / 해시태그 / 키워드 / 작성자`가 동작하는지 확인합니다.
- 쉼표로 여러 검색어를 입력해도 검색어가 사라지지 않는지 확인합니다.
- 추천 태그, 카드 태그, 작성자 닉네임 클릭 시 Home 검색 결과로 자연스럽게 이동하는지 확인합니다.
- 카드 클릭 시 상세 모달이 열리고, 모달 바깥 클릭으로 닫히는지 확인합니다.

## Auth

- 관리자 계정 로그인은 우선 실제 `/api/auth/login` 응답 토큰으로 동작해야 합니다. 테스트 계정은 백엔드 시드/환경 설정과 맞춰 확인합니다.
- 백엔드 로그인 요청이 timeout 되는 경우에도 프론트는 관리자 데모 세션으로 자동 진입하지 않아야 합니다. 관리자 QA 데모는 실제 로그인 흐름과 분리된 명시적 개발 설정에서만 사용합니다.
- 회원가입 후 `ttalkak_access_token`이 localStorage에 저장되는지 확인합니다.
- 로그인 후 보호 API 요청에 `Authorization: Bearer ...` 헤더가 붙는지 확인합니다.
- 토큰이 없거나 만료되어 401이 오면 로그인 팝업이 열리고 토큰 상태가 정리되는지 확인합니다.
- 권한이 없는 작업에서 403이 오면 권한 없음 안내가 뜨는지 확인합니다.
- 회원탈퇴는 `DELETE /api/auth/withdraw`를 호출하고, 성공 시 토큰과 로그인 상태가 초기화되는지 확인합니다.
- Google 로그인/회원가입 버튼은 현재 데모 흐름이며 실제 OAuth 완료 흐름은 백엔드 확정 후 재연동합니다.

## Make

- Make 전송 시 Spring Boot `POST /api/prompts/improve`만 호출되는지 확인합니다.
- 브라우저 Network 탭에 FastAPI `/query`, 포트 `8000`, RAG 서버 URL, AI provider endpoint로 직접 나가는 요청이 없는지 확인합니다.
- FastAPI `/query`, RAG, Vector DB, LLM 호출은 Spring Boot 뒤에 숨겨져 있어야 합니다.
- Make 진입 시 `GET /api/make/threads`가 200으로 응답하는지 확인합니다.
- Make 진입 시 `GET /api/make/folders`가 200으로 응답하는지 확인합니다.
- 프롬프트 전송 시 `POST /api/prompts/improve`가 호출되는지 확인합니다.
- RAG 응답이 `improvedPrompt`, `improved_prompt`, `answer`, `text`, `content` 중 어떤 필드로 와도 결과 카드가 비지 않는지 확인합니다.
- RAG가 추가 질문 모드로 응답하면 질문 목록이 assistant 메시지로 보이는지 확인합니다.
- 404는 요청한 리소스 없음으로 처리되고, RAG 근거 없음으로 표시되지 않는지 확인합니다.
- RAG 근거 없음은 `200 OK` + `rag_status: "no_evidence"` 형태로 내려왔을 때 기본 첨삭 결과와 안내가 표시되는지 확인합니다.
- 429, 500, 503, 504 상황에서 데모 첨삭 fallback 안내가 표시되는지 확인합니다.
- 새 대화 저장 시 서버에서 받은 `id` 또는 `threadId`가 프론트 상태에 유지되는지 확인합니다.
- 폴더 생성 직후 이동할 때 서버 folder id가 없으면 임시 `folder-...` id를 `PATCH /api/make/threads/:id/folder`에 보내지 않는지 확인합니다.
- 폴더 이동 시 thread id가 서버 숫자 id인지 확인합니다.
- 같은 첫 입력을 다시 보내도 기존 대화가 덮어써지지 않고 별도 대화로 남는지 확인합니다.

## Share

- 로그아웃 상태에서는 Share 진입 또는 공유 시 로그인 안내가 뜨는지 확인합니다.
- 로그인 상태에서 제목과 프롬프트가 있으면 공유 가능한지 확인합니다. 해시태그는 선택 사항입니다.
- 해시태그 없이 공유하면 태그 없는 게시물로 등록되고, 해시태그 입력은 기존 태그 우선 추천, 검색 결과 없음일 때 새 태그 추가 흐름으로 동작하는지 확인합니다.
- 공유 성공 후 Home 최신 정렬 또는 검색에서 방금 공유한 프롬프트가 보이는지 확인합니다.

## My Page

- 로그아웃 상태에서는 My page 메뉴가 보이지 않는지 확인합니다.
- 신규 로그인 사용자의 My page는 기본적으로 비어 있고, 데모 데이터 채우기/숨기기 상태가 구분되는지 확인합니다.
- 내 보관함, 내가 만든 프롬프트, 댓글 관리, 신고 내역 탭이 표시되는지 확인합니다.
- 저장 취소 후 My page를 벗어나면 목록에서 제거되는지 확인합니다.
- 내가 만든 프롬프트의 공유/비공개 전환이 작성자 권한에서만 가능한지 확인합니다.
- 댓글 관리의 원문 보기, 수정, 삭제가 동작하는지 확인합니다.

## Prompt Detail And Comments

- 상세 모달에서 데스크톱은 좌측 프롬프트 / 우측 댓글 2단으로 보이는지 확인합니다.
- 댓글 영역은 기본 펼침이며, 필요하면 접기/펼치기가 가능한지 확인합니다.
- 댓글/대댓글 작성, 수정, 삭제, 좋아요, 신고가 권한에 맞게 동작하는지 확인합니다.
- 답글이 있는 댓글을 삭제하면 답글은 유지되고 원댓글 자리에 `삭제된 댓글입니다.`가 남는지 확인합니다.
- 로그아웃 상태에서 저장, 좋아요, 댓글, 공유, 신고, 폴더 관리 등 로그인 필요 기능이 막히는지 확인합니다.

## Admin

- 관리자 권한 계정으로 로그인했을 때만 Admin 메뉴가 보이는지 확인합니다.
- 관리자 계정에서 Admin 화면을 닫아도 Home 검토 화면만 접근 가능하고, Make/My page/Share 메뉴는 숨겨지는지 확인합니다.
- 관리자 계정에서는 My page 메뉴가 숨겨지고, 개인 신고 내역 대신 Admin > 신고 관리에서 운영 신고를 처리하는지 확인합니다.
- 신고 관리 / 프롬프트 관리 / 태그 관리가 사이드바 하위 메뉴로 표시되는지 확인합니다.
- 관리자 원문 보기는 Execute, 좋아요, 저장, 공유, 일반 신고 같은 사용자 액션 없이 운영 액션만 보여야 합니다.
- 신고 관리는 원문 보기, 수정 요청, 게시물 숨김/숨김 해제, 검토 완료, 기각, 댓글 삭제 흐름을 확인합니다. 처리 완료/기각 신고는 최종 상태로 유지하며, 프롬프트 영구 삭제는 현재 백엔드 정책에 포함하지 않습니다.
- 댓글 신고에서는 게시물 작성자와 댓글 작성자 맥락이 구분되어 보이는지 확인합니다.
- 프롬프트 관리는 관리자가 직접 본문을 수정하지 않고 수정 요청, 숨김/해제 중심으로 동작하는지 확인합니다. 숨김은 복구 가능한 소프트 삭제입니다.
- 태그 관리는 검색, 상태 필터, 사용량/최신 정렬, 검토 완료, 반려, 추천 제외/복구가 구분되는지 확인합니다. 반려 태그는 최종 상태이며 승인 태그만 추천 제외/복구할 수 있습니다.

Additional admin check:

- Admin prompt review: click an author nickname and confirm the user activity lookup shows authored prompts, comments, replies, reports made, and reports received.

## Known Partial Areas

- 일부 화면은 API 호출 후에도 optimistic local state를 먼저 갱신합니다. 실패 rollback은 다음 연동 단계에서 더 보강해야 합니다.
- My page와 Admin의 전체 데이터는 백엔드 API 계약이 확정되면 서버 응답 기준 렌더링으로 교체해야 합니다.
- Google OAuth2는 백엔드 로컬 검증이 완료된 기능입니다. 운영 배포 전에는 Google Cloud Console의 실제 프론트 도메인 등록과 관련 환경변수 설정을 확인합니다.
- Make thread delete는 현재 백엔드 계약에 없으므로 로컬 전용 동작입니다.
- RAG의 최종 응답 스키마가 확정되면 `src/api.js`의 `normalizeImproveResult()`를 그 계약에 맞춰 더 좁게 정리할 수 있습니다.
