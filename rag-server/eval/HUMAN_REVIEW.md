# 사람 판단이 필요한 부분 (딸각 효과 측정)

> 이 문서는 **사람이 해야만 하는 일**만 모았다. 코드로 할 수 있는 검증은 이미 끝났고 결과는
> `WORKLOG.md`(2026-09-16 ~ 09-20)에 있다.
> 작성 2026-09-22. 담당자가 정해지면 각 항목의 "상태"를 고칠 것.

## 왜 사람이 필요한가

딸각의 효과는 "결과물이 사용자 요청을 얼마나 충족했는가"로 잰다. 그 판정을 지금은 **LLM 판정기**가 한다.
판정기가 맞는지 확인하려면 **정답**이 필요한데, 정답은 사람만 만들 수 있다. 지금까지 확인한 것은
판정기가 "내용을 지우면 알아본다"는 최소 민감도뿐이다(10/10, `eval/req_sensitivity.py`).
**사람 판단과 얼마나 맞는지는 모른다.**

또 하나, 지금 평가셋의 라벨은 **작성자 1인(Claude)** 판단이다. 사람마다 갈릴 수 있는 항목이 실제로 있었다.

## 1. 요구사항 판정기 대조 — **가장 중요, 먼저 할 것**

**무엇**: 결과물 20건 · 질문 95개에 **두 사람이 각자** 예/아니오로 답한다.
**왜**: 요구사항 충족률이 채점기의 주 지표인데, 판정기 수치를 믿을 근거가 아직 없다.
**드는 시간**: 한 사람당 약 1시간. 전문 지식 필요 없음.

### 하는 법
```bash
cd rag-server
python3 -m eval.human_review build      # 이미 만들어 둠 — 다시 만들 필요 없음
```
- 읽을 것: `eval/human_review/outputs.md` (사용자 요청 + AI 결과물 20건)
- 채울 것: `eval/human_review/sheet_A.csv`, `sheet_B.csv` — 두 사람이 **서로 보지 않고** 각자 한 부씩.
  엑셀·구글 시트로 열어 `답` 칸에 `예` / `아니오`(조건부 질문은 `해당없음`)만 적는다. 헷갈렸으면 메모 칸에 이유를 쓴다.

### 답할 때 기준
- **사용자 요청만 본다.** 문체가 마음에 드는지, 길이가 적당한지는 보지 않는다.
- 결과물에 **실제로 있을 때만 '예'**. 애매하거나 일부만 있으면 '아니오'.
- 분량·줄 수 질문은 **머리말("다음은 ~입니다")과 맺음말 한 줄을 빼고** 센다.
- `⟦자리표시자⟧`나 `[회사명]` 같은 빈칸이 질문이 묻는 내용 자리에 있으면 '아니오'.

### 끝나면
```bash
python3 -m eval.human_review judge      # 같은 질문을 판정기에 물어 저장(하루 한도 때문에 시간이 걸릴 수 있음)
python3 -m eval.human_review agree      # 일치도 계산
```

### 합격 기준
| 항목 | 기준 | 못 넘으면 |
|---|---|---|
| 사람 A·B 일치도(κ) | **≥ 0.6** | 질문이 모호한 것 — 갈린 질문을 고치거나 평가셋에서 뺀다 |
| 판정기–사람 일치도 | 사람–사람 일치도와 **비슷한 수준** | 요구사항 충족률을 결론에 쓰지 않는다(참고치로만) |

## 2. 경계 사례 결함 라벨 확인

**무엇**: 아래 5건이 결함인지 두 사람이 판단한다. 10분이면 된다.
**왜**: 판정기가 "놓쳤다"고 기록했지만, **제 라벨이 엄격했을 가능성**이 있다. 사람이 정해야 판정기의 약점인지 아닌지 갈린다.

| 사례 | 무슨 일 | 지금 라벨 | 판정기 |
|---|---|---|---|
| up_15 금리 요약 | 원문 "중앙은행"을 "**한국은행**"으로 특정 | 지어내기 | 3회 모두 아니라고 봄 |
| up_16 공손한 메시지 | 원문에 없던 "**오늘 중으로** 메일로" 추가 | 지어내기 | 3회 모두 아니라고 봄 |
| up_04 회의 요약 | "일정 논의" → "**일정 확정**" | 결함 아님(경계) | 3회 중 1회 지어내기 |
| up_47 문장 다듬기 | "새로 들어온" → "**새로 입사한**" | 결함 아님(경계) | 결함 아님 |
| up_45 사과문(Qwen) | 정보를 **먼저 되묻고** 템플릿을 줌 | 거부 아님(경계) | 미판정 |

원문·결과물은 `eval/defect_holdout2_set.json`, `eval/fresh_outputs_qwen_20260920.json` 에 있다.

## 3. 평가셋 라벨 검토

**무엇**: `eval/uplift_set_v2.json` 48문항의 요구사항·정답 항목이 **요청에서만 뽑혔는지**, 빠지거나 과한 게 없는지 본다.
**왜**: 라벨이 틀리면 그 위의 모든 수치가 틀린다. 지금은 1인 판단이다.
**우선**: 트랙 A(조건을 충분히 준 31문항) 먼저. 트랙 B는 질문이 1~2개뿐이라 급하지 않다.

특히 봐 줄 것:
- **`subjective: true` 표시가 맞는가** — 사람마다 갈리는 항목을 빼는 기준이다(현재 18개).
- **조건부 정답 항목(`conditional`)** — '해당 없음'이 가능한 게 맞는가(현재 2개).

## 4. 트랙 B 문항 교체 — **교체할 문항은 팀원이 써야 함**

**무엇**: `up_41`~`up_48` 8문항은 **Claude 가 지어낸 요청**이다. 딸각을 써 본 적 없는 팀원이 쓴 실제 요청으로 바꾼다.
**왜**: 딸각의 효과가 가장 클 만한 "조건이 부족한 요청"인데, 만든 사람이 평가 도구를 만든 쪽이면 유리하게 기울 수 있다.
**어떻게**: 딸각 결과를 **보지 않은 상태**에서, 평소 AI에게 던지듯 짧은 요청을 8개 쓴다. (예: "회식 공지 써줘" 수준)
`eval/gen_set.json`·`eval/halluc_set.json` 과 겹치면 안 된다(테스트가 막는다).

## 5. 두 결과 비교 선호(트랙 B) 대조 — 나중

**무엇**: 같은 요청의 두 결과물 중 어느 쪽이 나은지 사람이 고른다(순서를 가린 채).
**왜**: 트랙 B("도움이 되는가")의 주 지표라, 판정기 선호가 사람 선호와 맞는지 확인해야 한다.
**언제**: 트랙 B 측정을 시작할 때. 지금 돌고 있는 측정은 트랙 A 라 아직 필요 없다.
