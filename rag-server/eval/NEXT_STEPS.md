## 2. 정해야 할 것 (5번 κ 결과를 보고)

### 판정 백엔드
본 측정·사람 대조·결함 판정 검증이 **모두 같은 판정기**를 써야 한다 — 다른 판정기를 검증해 놓고
그 κ 로 본 측정을 믿을 수 없다. 세 도구 모두 `GEN_PRIMARY`(지금 `.env` = gemini)를 따르고,
`--backend groq|gemini` 로 고정할 수 있다. 판정 모델이 섞이면 `report` 와 `human_review judge` 가 경고·거부한다.

| | Groq (`gpt-oss-120b` 판정) | Gemini (`generator.default_model` — 지금 `gemini-3.6-flash`) |
|---|---|---|
| 결함 판정기 검증 | 조정용·별도 검증 2회 완료 | 조정용 9/9·12/12, 별도 검증 1차 3/3·12/12, **별도 검증 2차 9/9·51/51·일관성 20/20** (같은 표본 Groq: 3/9·47/51·19/20). Groq 가 3회 모두 놓친 미묘한 변경(up_15 '한국은행', up_16 '오늘 중으로')을 3/3 잡고 오탐 0. 단 그 두 건이 결함이라는 라벨 자체가 2번(경계 사례) 사람 확인 대상이다 |
| 요구사항 판정기 검증 | 5번 κ 로 | 5번 κ 로 (judge 를 Gemini 로 받으면 됨) |
| 한도 | 무료: 하루 **토큰** 20만 | **유료 Tier 1**(AI Studio `TTalkak` 프로젝트, 11-12 확인) — 트랙 A 규모로는 한도에 안 걸린다 |
| 비용(3조건×3회) | — | 약 **$4~5(₩6~7천)**, 최악 $15. 단가 입력 $0.75·출력 $3.75 /1M(사고 토큰도 출력 과금, 2027년부터 2배) — 실측 기록당 실행 ~1.2K·결함 판정 ~1.3K 토큰, 딸깍 생성 ~6.6K |
| 트랙 A 최소(2조건×1회, 217요청) | 약 **3.8일** | 약 **30분**(실측 기록당 25~32초, 요청 한도에 안 걸리면) |
| 트랙 A 3조건×3회(1,023요청) | 약 **19.3일** | 약 **2~3시간**(같은 조건) |

**권장: Gemini.** 같은 별도 검증 표본에서 결함 판정이 Groq 보다 낫고(9/9 vs 3/9, 오탐 0 vs 4), 한도도 토큰이 아니라 요청 수라
트랙 A 를 며칠이 아니라 몇 시간에 끝낼 수 있다(세 조건 모두 Gemini 실호출 확인, 유료 Tier 1). 조건 두 가지:
① 2번 경계 사례에서 사람도 up_15·16 을 결함으로 봐야 'Gemini 가 더 잘 잡는다'가 확정된다.
② 1번 κ 의 판정기 답(`human_review judge`)도 Gemini 로 받는다 — `.env` 가 지금 그렇게 돼 있다.

### 반복 횟수
- **1회**: 빠르지만 같은 요청을 다시 돌렸을 때의 흔들림을 못 본다 — "운이었나"를 가를 수 없다.
- **3회**: 문항별 흔들림(`within_spread`)을 보고 차이가 흔들림보다 큰지 말할 수 있다. 발표에서 결론을 말하려면 이쪽.

권장: **3조건×3회**(기본값). 유료 Tier 1 이라 한도 걱정이 없고 비용은 약 $5다.

## 3. 명령 모음 (rag-server/ 에서)

```bash
# 5. 사람 대조 — 1번이 다 채워진 뒤
python3 -m eval.human_review judge          # 판정기 답 받기(본 측정과 같은 백엔드)
python3 -m eval.human_review agree          # 일치율·κ·AC1 — 분류별(객관·주관·정답) + 덧붙임(x1) 따로. 합격은 객관 AC1 ≥ 0.6

# 결함 판정기 재검증(판정 백엔드를 바꾸면 다시)
python3 -m eval.defect_canary --set defect_holdout2_set.json --repeats 3 --sleep 4

# 8. 트랙 A — 먼저 호출 수만 보고, 그다음 실행
python3 -m eval.uplift_score --track A --dry-run
python3 -m eval.uplift_score --track A --out eval/results/uplift_trackA_<날짜>.json

# 9. 보고서(중단돼도 같은 --out 으로 다시 돌리면 이어서 한다)
python3 -m eval.uplift_score --report eval/results/uplift_trackA_<날짜>.json
```

딸깍 조건(`ttalkak`)은 운영과 같은 검색·생성을 거치므로 **도커의 DB·임베딩이 떠 있어야** 한다.

## 4. 버리는 것 · 하지 않는 것

| 무엇 | 이유 |
|---|---|
| `eval/results/uplift_trackA_20260922.*` (18/62 에서 중단) | 판정 프롬프트 `req-v1` · 분량 판정 결함 수정 전 · Groq 판정 — 새 측정과 섞을 수 없다 |
| 질문 문구 미리 다듬기 | 일치도가 모호한 질문을 찾는 장치다. 미리 고치면 잴 대상이 사라진다. AC1 < 0.6 인 분류의 갈린 질문만 그때 고친다 |
| 주관 질문 고치기 | 이미 주 지표에서 빠져 있다. 낮은 κ 는 "사람도 갈린다"는 근거로 쓴다 |
| x1(덧붙인 사실 오류)를 판정기에 묻기 | 사람 답이 모이기 전에 프롬프트를 바꾸면 `req-v3` 가 되어 재채점이 한 번 더 늘어난다 |
