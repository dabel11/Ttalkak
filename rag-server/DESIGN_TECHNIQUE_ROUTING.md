# 기법 라우팅 설계 — 유사도 검색에서 판단 기반 조회로

**상태**: 설계 초안 (미구현). 2026-08-15
**배경**: WORKLOG 2026-08-15 「검색 구조 정밀 진단」

---

## 1. 왜 바꾸는가

현재 파이프라인은 사용자 요청으로 기법 카드를 **유사도 검색**한다. 측정 결과 이 방식이
원리적으로 맞지 않는다.

- 질의↔카드 평균 유사도 **0.440**, 최대 0.586 — 그런데 **카드↔카드 평균은 0.677**.
  질의에 가장 잘 맞는 카드보다 아무 카드 두 장이 더 닮았다.
- 리랭커 로짓이 실제 요청에 대해 **0.0000** — 완전 무관 질의와 동점.
- 형태를 카드 쪽에 맞출수록 유사도는 오르고 **정확도는 떨어진다**(0.190 → 0.095).
- Recall@5 **0.215** (gold 라벨 대비, 라벨 미검증)

유사도가 답하는 질문은 *"이 둘이 같은 것에 대한 텍스트인가"*다.
딸깍이 필요한 질문은 *"이 요청의 결핍을 이 기법이 메우는가"* — **증상↔처방 관계**다.
둘은 닮을 이유가 없다.

**핵심**: 기법명으로 질의하면 Hit@1 **1.000**이다. 인덱스는 완벽하다.
문제는 "어떤 기법이 필요한가"를 **판단하는 주체가 파이프라인에 없다**는 것이다.

```
현재:  요청 ──유사도──> 기법 5장 ──> 생성
설계:  요청 ──판단──> 필요 기법 축 ──조회──> 카드 ──> 생성
```

임베딩은 버리지 않는다. 역할이 **탐색에서 조회로** 바뀐다.

---

## 2. 왜 analyzer 인가

판단에는 추론이 필요하고, 이미 요청을 읽고 구조를 뽑는 컴포넌트가 있다.

`app/rag/analyzer.py` — MAKE 1단계. `{taskType, fields[{name, role, status, value}]}` 출력.
- 이미 `taskType`(작업유형)을 판정한다
- 이미 필드의 **결핍 상태**(`empty`/`filled`)를 판정한다 — 결핍이 곧 기법 수요다
- temp 0.2 결정성 우선, 실패 시 `None` 반환 → **무회귀 폴백이 이미 있다**
- 실측 근거: 분석·생성 분리로 일관성 0.23~0.75 → 0.86~1.00 (2026-07-30)

새 컴포넌트를 만들지 않고 여기에 축을 하나 더 얹는 게 가장 짧다.

## 3. 설계

### 3.1 기법 축(technique axes) — 통제 어휘

카드의 `Category` 는 쓸 수 없다. **170장에 고유 카테고리 54종**이고
`Reasoning`/`Reasoning Prompting`, `Optimization`/`Prompt Optimization` 처럼 표기가 분열돼 있다.
LLM 추출 자유텍스트라 통제 어휘가 아니다.

대신 **고정 축 10~12개**를 정의한다. 축은 "요청이 무엇을 필요로 하는가"의 언어여야지
"기법이 무엇인가"의 언어여서는 안 된다.

| 축 | 언제 필요한가 |
|---|---|
| `role_assignment` | 전문성·관점 기준이 결과를 좌우할 때 |
| `output_format` | 표·목록·JSON 등 산출 구조가 지정됐거나 필요할 때 |
| `length_control` | 분량·개수가 지정됐을 때 |
| `tone_style` | 톤·문체·독자 눈높이가 지정됐거나 필요할 때 |
| `constraints` | 금지·필수 포함 조건이 있을 때 |
| `decomposition` | 작업이 여러 단계로 나뉠 때 |
| `examples` | 예시 제시가 품질을 좌우할 때 |
| `grounding` | 사용자가 준 원문에 답을 묶어야 할 때 |
| `uncertainty` | 미확정 정보를 빈칸·질문으로 남겨야 할 때 |
| `context_isolation` | 이전 주제와 섞이면 안 될 때 |
| `comparison` | 둘 이상을 비교·평가해야 할 때 |
| `extraction` | 원문에서 특정 항목을 뽑아내야 할 때 |

축 수가 관건이다. 너무 적으면 변별력이 없고, 너무 많으면 8b가 못 고른다.
**12개로 시작해 측정으로 조정한다.**

### 3.2 analyzer 출력 확장

기존 출력을 유지하고 필드를 **추가만** 한다(하위 호환).

```json
{
  "taskType": "글쓰기",
  "fields": [...],
  "techniqueAxes": ["tone_style", "length_control"]
}
```

- 최대 3개. 많이 고르면 지금과 같은 "아무거나 5장" 상태로 회귀한다.
- 축 이름은 **위 목록에서만** 고른다. 자유텍스트 금지.
- 못 고르면 `[]` → 호출자는 **기존 유사도 검색으로 폴백**한다(무회귀).

⚠️ 8b 리스크: 현 analyzer 주석에 *"구체적인 예시 하나를 길게 쓰면 8b가 그 예시를 무관한
요청에도 복사한다"* 는 실측 경고가 있다. 축 선택도 같은 위험이 있으므로
**축 목록은 짧은 한 줄 설명만** 주고 시나리오 예시를 쓰지 않는다.

### 3.3 카드 태깅

170장 각각에 축을 1~3개 부여한다. 메타데이터에 `axes` 필드 추가.

- 방식: LLM 1회 배치(카드당 1회, 170회) → 결과를 사람이 검토
- 이건 **일회성 백필**이다. `ingestion/backfill_axes.py` 로 분리한다.
- 신규 카드는 인제스트 시 함께 부여한다.

### 3.4 조회

```
axes → 해당 축이 태깅된 카드 집합 → 그 안에서 임베딩 유사도로 top-k
```

- 축 필터가 **후보를 좁히고**, 임베딩이 **그 안에서 순위**를 정한다.
- 축이 비면(폴백) 기존 경로 그대로.
- 축에 카드가 너무 적으면(<3) 인접 축까지 확장.

임베딩을 이 위치에서 쓰는 건 타당하다 — 같은 축 안의 카드끼리는 **같은 종류의 텍스트**라
유사도가 의미를 갖는다. 질의↔카드의 공간 분리 문제가 여기선 발생하지 않는다.

## 4. 검증

**수용 기준**: 같은 잣대 — `multi_turn_set.json` gold 대비 Recall@5.

| | 현재 | 목표 |
|---|---:|---:|
| Recall@5 | 0.215 | **≥ 0.50** |
| Hit@1 | 0.400 | 유지 이상 |

0.50 근거: 축 12개 중 정답 축을 맞히면 후보가 ~14장으로 좁혀지고, 그 안에서 top-5면
gold 4~5개 중 2~3개는 들어와야 한다. 이보다 낮으면 축 설계가 틀린 것이다.

**추가 확인**
- 축 선택 일관성 — 같은 요청 3회 반복해 축이 흔들리는지(8b 신뢰성)
- 폴백률 — `techniqueAxes` 가 빈 비율. 30% 넘으면 축 목록이 부족한 것
- end-to-end — `run_multi_turn_eval` 로 help/harm 재측정

⚠️ **gold 라벨은 아직 검증되지 않았다.** 작성자 1인 판단이므로 수용 기준으로 쓰기 전에
팀 검토가 필요하다. 그전까지 모든 수치는 잠정이다.

---

## 5. 순서

1. 축 어휘 확정 (12개) — 팀 합의 필요
2. `gold_techniques` 라벨 검토 — 수용 기준의 전제
3. 카드 170장 축 태깅 (일회성 배치 + 검토)
4. analyzer 출력에 `techniqueAxes` 추가
5. 조회 경로 구현 (축 필터 + 임베딩 순위)
6. Recall@5 측정 → 축 조정
7. end-to-end help/harm 재측정

**1·2번이 먼저다.** 축 어휘와 정답 라벨이 흔들리면 나머지를 측정할 수 없다.

## 7. 이 설계가 틀릴 수 있는 지점

정직하게 적어둔다.

- **8b가 축을 못 고를 수 있다.** 그러면 70b로 올려야 하는데 TPM 예산이 문제가 된다.
  측정 항목에 "축 선택 일관성"을 넣은 이유다.
- **축 12개가 잘못된 절단면일 수 있다.** 요청의 결핍이 축으로 깔끔히 안 나뉠 수 있다.
  이 경우 Recall 이 0.50 을 못 넘고, 축을 다시 설계해야 한다.
- **카드 태깅이 곧 정답 라벨이 된다.** 태깅이 틀리면 조회도 틀린다. 사람 검토가 필수다.
- **판단을 LLM에 맡기는 이상 판단 오류가 검색 오류를 대체할 뿐일 수 있다.**
  다만 현재 리랭커는 로짓 0.0000 — 판단을 아예 안 하고 있으므로 하한은 이미 바닥이다.
