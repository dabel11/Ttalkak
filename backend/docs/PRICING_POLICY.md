| 비회원 | 무료 | 총 3회 | 기존 체험 정책 유지 |
| FREE(로그인) | 월 0원 | 월 10회 | 서울 시간 월 단위 |

요금제 단계는 FREE(0원·10회), LIGHT(3,900원·30회), STANDARD(5,900원·70회), PRO(9,900원·150회)로 구성하는 **팀 검토안**이다. STANDARD를 주력 상품으로 제안한다. 위 세 유료 가격은 부가세 포함 가정이며, 아직 설문·유료 전환율로 검증되지 않았다. 비회원 누적 3회 체험은 유지한다.

원클릭 개선·Make는 같은 요청 횟수 한도를 사용한다. 모델의 출력 품질에 따라 무료/유료를 나누지 않는다. 저장/결과조회/적용/원본복원/동일 멱등 요청 재조회는 신규 AI 호출이 아니므로 사용 횟수를 추가 차감하지 않는다. 멀티턴의 새로운 AI 호출은 매번 1회다.

기존 **월 4,900원/300회**는 2027 정가 가정 시 AI 변동비만 약 **$5.796 (환율 1,341원 가정 시 약 7,770원)**으로 지속 가능하지 않다. 환율 1,341원은 모델 계산용 가정이며 실시간 환율이나 2027 확정 환율이 아니다.

- **잔여 약 3,089원/유료 가입자/월**, 인건비·환불·재시도·추가 서버/DB·광고비 등 미반영.

무료/유료 사용자 비율 상승, 긴 프롬프트, 추가 추론 호출, 토큰 단가 변경 시 손익이 크게 악화될 수 있다. 현재 Gemini 표본 21건만으로 상위 원가(P90/P99)를 알 수 없으므로 장문·멀티턴 데이터 추가 확보 전에는 실제 출시 가격을 확정하지 않는다.

### 신규 가입 및 기간 중 업그레이드: 테스트 결제 정책

- 가입 시 LIGHT 3,900원, STANDARD 5,900원, PRO 9,900원 **각 월 정가로 테스트 첫 결제**. 세 요금제 모두 카드 등록과 매월 정기 갱신을 지원한다.
- 사용 중인 유료 구독의 상위 요금제로 **즉시 업그레이드**할 수 있다. 중간 다운그레이드는 미지원(별도 기획 필요).
- **지금 결제할 차액 = 올릴 요금제 월 정가 차액 × 현재 결제 기간 남은 시간 비율**을 원 단위 올림한다. 서버의 `/api/me/billing/upgrade-quote?plan=...`가 최종 금액을 계산한다. 프론트는 금액을 직접 계산하거나 임의로 전송해 청구할 수 없다.
- 기존 이용 기간 시작·종료 시점과 소비 횟수는 유지한다. **이번 기간 추가 사용 가능 횟수 = (상위 등급 기본 횟수 − 현재 등급 기본 횟수) × 남은 기간 비율**을 회 단위 올림하며, 현재까지 누적 제공 횟수에 더한다. 다음 자동 갱신부터는 새 등급 정가와 전체 기본 횟수가 적용된다.
- 기존 월 30회 LIGHT에서 STANDARD 70회로 변경한다면, 월 중간 절반 시점에서는 **추가 약 1,000원** / 이번 기간 총 한도 **약 50회**, 다음 정기결제 **5,900원/70회**.
- STANDARD 70회 → PRO 150회, 월 절반 시점에서 **추가 약 2,000원** / 현재 기간 한도 **약 110회**, 다음 정기결제 9,900원/150회.
- LIGHT 30회 → PRO 150회, 월 절반 시점에서 **추가 약 3,000원** / 현재 기간 한도 **약 90회**, 다음 정기결제 9,900원/150회.
- 사용량의 **70% 이상** 사용 시 상위 요금제 추천 배너를 보여주며, 버튼을 눌러 서버 견적·다음 갱신액·추가 제공 횟수를 확인한 뒤에만 테스트 결제한다. 사용자 동의 없는 자동 업그레이드/추가 청구는 없다.
- 이미 진행 중인 주문의 가격·등급·추가 제공 횟수는 저장해 재조회에 사용한다. 결제 불확실 상태는 같은 주문번호로 재조회하고, 명백한 승인 거절은 기존 플랜 유지.
- **본 기능은 Toss 테스트 키(`test_ck_`/`test_sk_`)만 허용한다.** 운영 실결제 전환·환불·할인·실운영 DB 스키마 마이그레이션은 별도 검증 대상이다. 이전 PRO 테스트 금액 환경변수 4,900원은 새 정가와 일치하지 않아 설정 확인 전 테스트 결제가 거부되도록 한다.

## 3. 브랜치에서 준비한 구현

- `MEMBER_REQUEST_QUOTA_ENABLED` **기본 false**: 승인 전 횟수 차단을 자동으로 켜지 않는다.
- `FREE_REQUEST_LIMIT=10`, `LIGHT_REQUEST_LIMIT=30`, `STANDARD_REQUEST_LIMIT=70`, `PRO_REQUEST_LIMIT=150`의 설정값으로 4등급 요청 한도 로직을 구현했다. **`MEMBER_REQUEST_QUOTA_ENABLED=false`가 기본값**이므로 테스트 배포에서 한도 차단을 켜려면 별도 승인과 테스트가 필요하다.
- `MemberRequestGuard`가 실제 집계된 `snapshot.requests()` 기반으로 한도를 검사한다. 기존 토큰 한도 검사는 별도로 유지한다.
- `/api/me/usage`에 `requestLimit`, `requestRemaining`, `requestLimitReached`, `requestQuotaEnforced` 추가. 비활성화 시 `requestLimit`/잔여횟수는 null이다.
- 프론트는 서버가 요청 한도 활성화를 보고했을 때만 요청 횟수/잔여횟수를 노출한다.
- Spring은 RAG `/query`에 `request_id`를 보내고 같은 요청 키로 LLM 사용량을 저장한다. 비회원/요청 키 없는 신규 호출도 서버가 식별자를 만든다.

### 중요한 한계와 출시 조건

1. `rag-server/app/core/usage.py`의 `summary/records`는 **LLM 토큰만** 집계한다. Jina 리랭크 8,297토큰은 `MemberTokenUsage.totalTokens`에 포함되어 있지 않다. Jina와 LLM을 합쳐 회원 토큰 차감을 계산해서는 안 된다.
2. 현재 요청 횟수는 `member_token_usage`에 저장된 **LLM 사용량이 있는 호출 + 실제 RAG 404(no-evidence) 호출** 기준이다. RAG 404는 LLM 토큰을 만들어 넣지 않고 요청 1건으로만 기록한다. `usage=null`인 정상 응답은 누락으로 표시하고 회원 신규 호출을 보류하는 기존 보호 로직을 유지한다. 5xx/타임아웃/부분실패, 리트라이, 서버 재시작, 동시 요청의 실제 공급사 과금 대비 차감 규정은 추가 검증이 필요하다.
3. Jina 비용은 요청별 청구 토큰과 금액을 아직 Spring DB에 별도 적재하지 않는다. 요금원가 리포팅을 위해 RAG 계약과 데이터 스키마를 별도 확정해야 한다. AI 담당자 코드 임의 수정 금지.
4. 개발 브랜치만 변경. **토스 테스트 결제 기본값 4,900원, Railway 환경변수, 실제 결제, 공개 가격 UI, 자동 갱신은 변경하지 않는다.**
5. 팀 승인 후 가격/월 제공량을 다시 확정하고, `PRO_MONTHLY_PRICE_KRW`, API 응답·프론트 공개 표시·결제 테스트·실결제 준비는 별도 검증한다.
