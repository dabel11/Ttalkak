## 이 PR에서 추가한 처리와 남은 출시 조건

- BillingContext의 BILLING_MODE와 BILLING_STORE_SCOPE로 주문·구독·이용권을 분리한다.
  새 행에는 scope를 저장하고 기존 NULL은 test:legacy로만 해석한다.
  다른 scope의 유료 권한·사용량 기간·자동 갱신·주문 조회를 차단한다.
- 기본 설정은 test / test:legacy다. disabled는 결제사 호출을 차단한다.
  scope는 소문자 ASCII 영문·숫자·밑줄·하이픈만 허용한다. 대문자가 포함된 설정은
  시작 시 거부하며 자동 소문자 변환은 하지 않는다. Java와 MySQL의 대소문자 비교 차이로
  test:Legacy 등이 기존 NULL/test:legacy 데이터와 혼동되는 것을 방지한다.
  live는 독립적인 live: 상점 scope가 필요하며, 이 PR에서는 **실제 결제사 호출을 계속 차단**한다.
  라이브 키를 테스트 키 변수에 넣거나 모드만 live로 바꿔 실결제를 여는 방식은 지원하지 않는다.
- 신규 nullable 컬럼: 세 테이블의 billing_scope VARCHAR(80), billing_charges의
  refund_state VARCHAR(16), refund_reason VARCHAR(200), refund_idempotency_key VARCHAR(64),
  refunded_at DATETIME(6). 기존 데이터 삭제·scope 변환·백필을 자동 실행하지 않는다.
- 회원의 환불 검토 요청은 자동 갱신만 중지하며 결제사 취소나 이용권 회수를 실행하지 않는다.
- 관리자 승인에는 원 결제 금액, 기록 검토 확인, 사유가 필요하다.
  일반 구독 결제의 전액 취소만 처리하고 업그레이드·부분 취소·변경된 이용권은 별도 검토한다.
- 취소 전에 원 주문·paymentKey·유형·최초 금액·잔액을 조회 검증한다.
  전액 취소 CANCELED / balanceAmount=0 확인 후 해당 결제의 이용권만 회수한다.
- 취소 응답이 불확실하면 PENDING을 유지한다. 저장된 동일 멱등키를 사용하는 재시도와

  취소 PENDING 동안 새 AI 요청과 결제 갱신을 차단한다. 기존 사용량 기록은 삭제하거나 초기화하지 않는다.

- **남은 출시 조건:** PG 계약·상점·공개 정책 확정 및 원가 모니터링 준비, 라이브 전용 DB/계정 이관 설계,

### 합의된 가격과 원가 모니터링

임베딩, LLM, 외부 리랭커, 재시도·실패 호출의 실제 비용을 요청별로 측정한다.
평균뿐 아니라 긴 입력과 재개선 요청의 비용, 요금제 한도 전부 소진 시 비용도 계산한다.
PG 수수료는 자동결제 계약의 실제 요율을 사용하고 서버·DB 비용과 무료 회원 비용을 포함한다.
세금 처리와 고객 표시 가격은 사업자 과세 유형 및 판매 정책 확정 뒤 반영한다.
판매 가격은 사용자 확인으로 협의 완료됐다. 이를 수익성이 검증된 가격으로 안내하지 않는다.

## 관리자 환불 운영 API (테스트 환경)

1. GET /api/admin/billing/refunds?state=REQUESTED 로 검토 대상(최대 50건)을 확인한다.
   지원 상태는 REQUESTED / PENDING / DONE / REJECTED다.
2. 원 주문, 사용량, 고객 요청과 정책을 검토한 후
   POST /api/admin/billing/refunds/{orderId}/approve 에 다음 본문을 보낸다.
   {"expectedAmount":3900,"recordsReviewed":true,"reason":"원 결제와 환불 요청 검토 완료"}
   금액은 예시이며 반드시 해당 주문 조회 값으로 바꾼다. 최초 취소 요청에 저장된 멱등키가 재시도에도 유지된다.
3. 불확실한 취소는 POST /api/admin/billing/refunds/{orderId}/reconcile 로 조회만 수행한다.
   아직 전액 취소가 아니라면 PENDING을 유지한다. 재승인은 같은 키·같은 금액으로만 취소를 재시도한다.
4. REQUESTED 단계의 거절만 POST /api/admin/billing/refunds/{orderId}/reject
   {"reason":"별도 검토 결과 안내"} 로 처리할 수 있다. 취소 PENDING은 거절해서 닫을 수 없다.
5. MEMBER_REQUEST_IN_PROGRESS면 활성 AI 요청 완료 또는 기존 사용량 복구 절차를 먼저 확인한다.
6. BILLING_REFUND_MANUAL_REVIEW는 자동 환불을 강제하지 않는다. 업그레이드/부분 취소,
   변경된 이용권은 정책·권한 대사 구현 후 처리한다.

이 API는 관리자 인증이 필요하며 결제키·빌링키를 응답하지 않는다.
환불 요청을 받았다는 사실과 환불이 완료됐다는 사실을 구분해서 안내한다.
거절 후 자동 갱신은 자동으로 재개하지 않는다. 회원이 명시적으로 다시 활성화해야 한다.
현재 상점 scope를 임의로 변경하면 기존 NULL/다른 scope의 구독이 제외되므로,
실제 MID별 이름을 새로 정할 때에는 별도 복구·이관 검토를 먼저 한다.
회원별 구독 unique 제약과 결제 reference unique 제약은 유지한다.
같은 DB의 기존 테스트 구독을 자동으로 라이브 구독으로 바꾸지 않는다.

## 학과 경비 지원 확인 항목

학과는 졸업프로젝트 경비를 지원하는 것으로 안내받았다. 유료 운영은 팀 내부에서 협의한다.

수익 발생 시 경비 지원이나 정산에 영향을 주는 조건이 있는지 확인한다.
학과 지원분은 개인이 부담한 비용으로 중복 정산하지 않는다.

사용자는 판매 가격 협의 완료 및 PR #57에 요금제 출시 범위를 포함하도록 요청했다.
사업자등록·PG 계약은 아직 진행 중이라고 확인했다.

- 공개 /pricing 화면은 판매 가격과 FREE 10 / LIGHT 30 / STANDARD 70 / PRO 150회 한도를 안내한다.
- production 기본 화면의 유료 신청 버튼은 비활성이고, 결제 준비 중임을 명시한다.
- 로그인 회원은 현재 요금제·사용량을 조회할 수 있다. 한도 소진 시 구매할 수 없는 상품으로 업그레이드를 권하지 않는다.
- 로컬 또는 명시적으로 켠 테스트 미리보기에서는 기존 테스트 결제 흐름을 유지한다.
- 가격 공개, PR 병합·배포, 실결제 활성화는 별개의 단계다.
- 현재 라이브 결제 차단은 유지한다. PG 자동결제 계약·라이브 키·고객 안내 및 정책·데이터 이관 준비가 끝나면 라이브 키 경로를 구현하고 실제 승인·취소를 검증한 뒤 구매 기능을 연다.
