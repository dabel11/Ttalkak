# TTALKAK 졸업 전시회 부스 운영 및 체험 점검안

> 2026-10-19 수정 · `develop` 기준 · 발표회가 아닌 **자유 관람형 졸업 전시회**를 위한 운영안.
> 방문객에게 5분 발표나 교수님 질의응답을 진행한다고 가정하지 않는다.
> 장소/부스 장비/관람 시간/QR 코드·배포 URL은 확정되지 않았으므로 임의로 적지 않는다.
> 실제 사용자 계정, AI 유료 API, 게시글 생성은 사전 확인된 범위에서만 사용한다.

## 1. 방문객에게 보여 줄 가치

**문제:** AI를 쓰려고 해도 사용자의 목적과 조건을 정확하게 표현하기 어렵다.

**TTALKAK:** 사용자의 의도를 바탕으로 프롬프트를 개선하고, 필요한 정보가 부족할 때에는 지어내지 않고 질문한다. 웹·Chrome 확장 프로그램에서 사용하고, 로그인하면 개선 대화와 프롬프트를 저장·재활용할 수 있게 설계했다.

**현장에서 확인할 핵심:** 설명이 아닌 **직접 입력 → 개선 결과 확인 → 선택적 질문 또는 재개선**을 방문객이 짧게 경험할 수 있게 한다. 실제 개선 성공/환각 방지 효과는 시연 및 평가 증빙이 확보된 범위만 설명한다.

## 2. 자율 체험 흐름 (권장 60~120초, 고정 시간표 아님)

| 체험 단계 | 방문객이 하는 일 | 화면/운영에서 확인할 것 |
| --- | --- | --- |
| ① 진입 | 전시용 웹 화면 열기 | 바로 입력 가능한 화면, 직관적 시작 동선, 상태 표시 |
| ② 입력 | 합성 예시 문장을 선택하거나 직접 입력 | 개인정보·비밀번호·기밀정보 입력 금지 안내 |
| ③ 결과 확인 | 개선된 프롬프트 및 추가 질문 확인 | 입력 조건 보존, 없는 정보 임의 추가 금지, 실행 가능한 개선안 |
| ④ 더 개선 | 조건 하나 추가해서 재요청 | 앞서 제공된 사용자 의도·제약 유지, 중복 클릭 방지 |
| ⑤ 다음 관람객 | 대화 종료 후 새 체험 시작 | 이전 방문객의 대화·인증정보·화면 잔존 방지 |

시간이 짧은 관람객은 **②→③**만 체험해도 된다. 전시 공간에서 제한 없는 실제 AI 요청을 장시간 반복하지 않는다.

안정적으로 시험할 **합성 입력 세트 A(명확한 작업), B(주제 없음), C(후속 조건 유지)**는 [데모 입력 카드](GRADUATION_DEMO_CASES.md)에 있다. 이 예시들의 결과는 실제 AI 검증 전까지 성공이라고 표현하지 않는다.

## 3. 체험 단말 및 개인정보 안전

- 부스 컴퓨터를 제공하는 경우: 관리자 계정/DB 접속/PG 테스트 화면은 열어 두지 않는다. 실사용자 로그인을 이용하지 않으며, 브라우저 자동완성·비밀번호 저장 기능을 끈다.
- **방문객의 자율 입력을 허용한다면** 이름, 연락처, 개인 문서, 비밀번호, 회사·학교 기밀 입력 금지를 화면 또는 부스 안내로 명확히 표시한다.
- 체험이 끝날 때는 앱에서 새 대화로 전환하고 **실제로 세션 및 로컬 브라우저 상태가 지워지는지** 사전 검증한다. 단순 화면 새로고침을 개인정보 삭제로 간주하지 않는다. 인증 계정 사용 시 로그아웃 및 데이터 분리 검증도 필요하다.
- 사용량 제한/비용: 비회원 3회 정책이 있다. 자율 체험에서 어떤 리셋 방식으로 운영할지, 방문객 회차와 게스트 식별 방식이 충돌하지 않는지 사전 합의가 필요하다. **쿼터 우회·실 계정 대량 생성·무제한 외부 AI 호출을 임의로 적용하지 않는다.**
- 로그인/저장 시연은 **사전에 승인된 테스트 계정**에서 담당자가 수행한다. 일반 관람객에게 운영 계정이나 테스트 비밀번호를 공유하지 않는다.
- QR 안내가 필요하면 확정된 공식 웹/확장 설치 링크를 사용한다. 주소를 임의 작성하지 않고 직접 열리는지 전시장 네트워크에서 확인한다.

## 4. 전시회 전 리허설 체크

- [ ] PC/태블릿/화면/확장 프로그램 등 실제 제공될 장비 및 화면 비율 확정
- [ ] 전시장 Wi-Fi 또는 유선망에서 실제 Web·Backend·RAG 연동과 응답 지연 확인
- [ ] 합성 입력 A/B/C 최소 1회씩 시험, 결과는 PASS/FAIL/SKIP로 기록
- [ ] 익명 3회 제한, 새 관람객 시작 상태, 중복 클릭, 요청 취소·지연 대응 확인
- [ ] 방문객의 이전 입력/로컬 저장/토큰이 다음 관람객에게 노출되지 않는지 확인
- [ ] 읽기 전용 공개 검사 `scripts/check-staging-readiness.py --security` 성공 확인 (단, 실제 생성 성공을 뜻하지 않음)
- [ ] #69의 개인정보 관련 수정이 아직 Draft인지, 실제 배포 SHA에 포함됐는지 구분
- [ ] 화면에 비밀번호/토큰/사용자 이름/결제 키 등 민감정보가 드러나지 않는지 최종 확인
- [ ] 실 RAG API 요청의 호출 수·비용과 오류 발생 시 대체 화면 운영 방식 승인

## 5. 장애가 나도 관람객 경험을 유지하는 방법

| 문제 | 대응 | 주의 |
| --- | --- | --- |
| 웹 화면/Backend 접속 불가 | 네트워크 확인 후 사전에 준비한 **합성 입력의 녹화 데모** 또는 검증된 스크린샷으로 전환 | 녹화 당시 시각·버전 표기. 현재 실서비스 동작이라고 설명하지 않음 |
| AI 요청 429/503 또는 지연 | 상태·재시도 안내를 보여주고 체험을 잠시 중단, 준비된 이전 결과 사례로 소개 | 방문객이 반복 클릭해 요금/차감이 늘지 않게 함 |
| 게스트 한도 소진 | 관람 방식 전환: 사전 녹화/설명, 또는 운영자가 승인한 테스트 흐름 | 제한을 우회하거나 무단 계정을 생성하지 않음 |
| 로그인/메일/확장 설치 실패 | 일반 공개 입력 화면에서 체험하거나 녹화 사례 활용 | Google·메일 기능 성공을 거짓으로 주장하지 않음 |
| 개인정보가 화면에 남음 | 즉시 체험 중지, 상태·로그 확인, 안전한 브라우저/앱 재설정 후에만 재개 | 개인정보가 포함된 화면을 촬영/공유하지 않음 |

부스에서 실결제·환불·운영 DB 수정으로 문제를 해결하려 하지 않는다.

## 6. 검증 결과 및 결과보고

- 기능 확인과 AI 프롬프트 **품질 향상**은 별개의 증거다. 평가 결과는 [증거 현황판](GRADUATION_EVIDENCE_STATUS.md) 및 [보고서 증빙 템플릿](GRADUATION_REPORT_EVIDENCE_TEMPLATE.md)에서 관리한다.
- 실제 생성형 AI/외부 검색, 사람 평가, 운영 MySQL 9 복구는 증거가 없으면 미완료로 기록한다.
- 전시 부스에서 수집하는 피드백/설문이 필요하다면 **수집 여부·목적·보관·동의 방침이 정해진 뒤** 설계한다. 방문객의 실데이터를 자동 수집하는 기능은 여기서 추가하지 않는다.
- 역할 소개는 PM·백엔드/통합, 웹·확장 UX, AI·RAG를 짧게 표시하되 팀원별 상세 기여는 최신 병합 기록을 확인해 적는다.
