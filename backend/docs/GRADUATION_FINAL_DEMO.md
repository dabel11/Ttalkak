# TTALKAK 졸업프로젝트 최종 시연 운영안

> 2026-10-19 초안 · `develop` 기준 · PM/백엔드 관점.
> 이 문서는 **발표 리허설과 결과 증빙을 준비**하는 자료이며, 실제 시연 성공 기록이 아니다.
> 보안/탈퇴/개인정보 패치는 [Draft PR #69](https://github.com/dabel11/Ttalkak/pull/69)에서 별도 검증한다.

## 1. 프로젝트 메시지

**문제:** AI에게 무엇을 어떻게 요청할지 모르면 원하는 답을 얻기 어렵다.

**해결:** TTALKAK은 사용자의 의도를 분석하여 프롬프트 개선안을 제공하고, 정보가 부족한 경우 선택적으로 질문한다. 환각을 줄이기 위해 사용자가 제공하지 않은 사실을 임의로 채우지 않는 것을 핵심 설계 원칙으로 한다.

**증명할 것:** 웹/확장 프로그램 → Spring Boot → FastAPI/RAG → 개선 응답 → 저장/재조회 연결이 작동하는지와, 원본 입력 대비 최종 AI 산출물이 실제로 나아지는지 **분리해** 검증한다. 아직 검증하지 않은 부분을 완료로 표현하지 않는다.

## 2. 5분 시연 구성 (합성 입력만 사용)

| 시점 | 시연 | 관찰 포인트 |
| --- | --- | --- |
| 0:00–0:40 | 문제·서비스 가치와 처리 흐름 소개 | 단순 문장 확장이 아니라 사용자의 의도 보존 |
| 0:40–1:40 | Web 또는 Extension에서 작업+주제가 명확한 합성 입력 | 개선된 프롬프트, 선택적 추가 질문, 바로 실행 가능 여부 |
| 1:40–2:25 | 동일 입력에서 사용자가 추가 정보를 입력한 뒤 다시 개선 | 이전 맥락·추가 조건 유지, 임의 사실 추가 방지 |
| 2:25–3:20 | **승인된 테스트 계정**으로 대화 저장·재조회 | 중복 요청 방지, 로그인 권한, 저장 지속성 |
| 3:20–4:10 | 평가 설계와 결과 표 소개 | 비교 모델·문항 수·승률/오류율·사람 평가 여부를 구분 |
| 4:10–5:00 | 구현 분담·남은 한계·결론 | PM/백엔드, 프론트/확장, AI/RAG 기여 모두 언급 |

시연에는 실제 사용자 정보·인증 토큰·결제·관리자 계정 화면을 넣지 않는다. AI 요청은 사전 합의한 호출 수·비용 한도에서만 실행한다.

## 3. 리허설 전 완료 기준

- [ ] 시연용 Web/Extension 및 Backend/RAG 배포 커밋과 URL을 기록한다. `/healthz` 성공만으로 AI 성공을 단정하지 않는다.
- [ ] 원본 요청·후속 요청·개선 프롬프트·최종 실행 결과를 **민감정보 없는 합성 예시**로 선정한다.
- [ ] 안정적으로 재현되는 첫 턴과 추가 질문/개선 흐름을 확인한다. 질문만 반환되는 사례도 설계 근거와 함께 준비한다.
- [ ] 테스트 계정의 프롬프트 저장→로그아웃→재로그인→재조회 확인. 테스트 데이터는 승인된 범위에서만 생성한다.
- [ ] 401/403/429/503 실패 시 문구, 사용자 데이터 유실 여부와 서버 재시도 정책을 확인한다.
- [ ] 증거: 실행 시각, 배포 커밋, 기능, 기대 결과, HTTP 상태, 합격/미완료 및 이슈 번호만 저장한다.
- [ ] 시연 전날과 당일 공개 읽기 전용 검사를 실행한다: `python3 scripts/check-staging-readiness.py --origin https://web-production-a82d94.up.railway.app --security`.

## 4. AI 효과 검증을 발표에 연결하는 방법

기존 `rag-server/eval/uplift_set_v2.json` 평가셋에는 **48문항(Track A 31, Track B 17)** 이 있다.

- **Track A — 망치지 않는가:** 조건이 충분한 입력이 개선 뒤에도 요구사항을 유지하는지 확인한다.
- **Track B — 도움이 되는가:** 조건이 모자란 입력에서 실제 결과물의 유용성이 증가하는지 확인한다.
- **다중 턴:** 기존 `multi_turn_set.json`의 10항목에 대해 `rag_off`, `rag_on`, `oracle`을 비교한다. 실행을 완료한 항목 수를 반드시 기록한다.
- **판정기 신뢰도:** 기존 `eval/HUMAN_REVIEW.md`가 제시한 사람 2명의 독립 채점(20결과, 95질문) 및 사람 간 κ ≥ 0.6 기준을 우선한다. 기록된 사람 평가가 없다면 품질 향상 수치를 확정하지 않는다.
- 실제 검색 지표(Recall@k, nDCG@5, MRR)와 **최종 사용자 결과물의 유용성**을 혼동하지 않는다. 동일 생성 모델·조건, 평가 데이터셋 버전, 비용과 실패율을 명시한다.

현재 체크인된 과거 자료 중 Track A 9문항의 raw/TTALKAK 기록은 **중간 결과**일 뿐, 전체 31문항의 효과를 증명하지 않는다. 수치를 채워 넣을 때 `실험 날짜 / n / 원본 결과 / 개선 결과 / 사람 검증 여부 / 신뢰도·한계`를 반드시 함께 적는다.

## 5. 장애 시 시연 대체 경로

1. 생성 API 503·시간초과: **실패 사실을 숨기지 않는다.** 공개 API·권한·재시도 정책을 설명하고, 사전에 녹화한 합성 입력 시연 화면으로 전환한다. 녹화 시각과 코드/배포 버전을 명시한다.
2. Google 로그인/메일 장애: 기존에 승인된 데모 계정의 로컬 인증·저장 흐름만 사용하며, Google 연결 성공을 주장하지 않는다.
3. RAG 검색 근거 부족: 사용자 추가 질문 UX를 보여주고, 임의 답변을 지어내지 않는 설계로 설명한다.
4. Railway 장애: 서비스 재배포·DB 초기화로 시연을 강행하지 않는다. GitHub Actions 검증 기록과 로컬 합성 CI 테스트를 발표한다.

## 6. 팀별 설명 순서

- **PM/백엔드:** 전체 설계·사용자 흐름 조율, Spring API·인증·사용량·커뮤니티·DB·통합 배포 및 검증
- **프론트엔드:** 웹/확장 프로그램의 입력·대화·개선/저장 UX, 브라우저에서 사용자 경험
- **AI/RAG:** FastAPI 기반 검색·재랭킹·LLM 개선·질문/근거 판단, 품질 및 오류 사례 분석

팀원별 최신 기여도 수치는 병합 기록을 보고 재확인한다. 발표 시간을 역할별로 임의 배분하기보다 **핵심 가치를 하나의 사용자 여정으로** 설명한다.

## 7. 최종 발표 자료에 넣을 증빙

[결과보고 증빙 템플릿](GRADUATION_REPORT_EVIDENCE_TEMPLATE.md)을 사용한다. 기능 테스트 성공, 운영 공개 GET 확인, AI 실제 품질 실험, 사람 검수, 운영 MySQL 9 복구 결과를 **각각 별도 증거로** 기록한다.

사업화용 실결제 활성화, 상용 사용자 데이터 운영, 부분 환불, 개인정보 보존 기간 확정은 본 학기 시연의 성공 조건에 포함시키지 않는다. 졸업프로젝트 완료 후 별도 로드맵으로 관리한다.
