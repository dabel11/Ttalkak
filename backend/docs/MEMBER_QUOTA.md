# 회원 사용량 한도와 요청 보호

## 기본 상태와 활성화

- `MEMBER_QUOTA_ENABLED=false`가 기본이다. 임의의 FREE/PRO 한도는 적용하지 않는다.
- `FREE_TOKEN_LIMIT=0`, `PRO_TOKEN_LIMIT=0`은 미설정이다. 응답의 limit/remaining은 null이다.
- 두 한도를 양수로 설정하면 비활성 상태에서 API에 한도 미리보기가 가능하다.
- 실제 RAG의 usage 반환·DB 집계 및 팀 정책 확인 후에만 quota-enabled를 활성화한다.
- 활성화했는데 한도 하나라도 0 이하이면 서버 시작을 실패시킨다.
- 기존 FREE 한국시간 월 단위 / PRO 결제 기간 단위와 전환 처리는 유지한다.

## API

`GET /api/me/usage`는 기존 필드를 유지하고 다음을 추가한다.

| 필드 | 의미 |
| --- | --- |
| used | totalTokens와 같은 실제 기록 토큰 총합 |
| limit | 현재 요금제 한도. 미설정이면 null |
| remaining | max(0, limit-used). 미설정이면 null |
| limitReached | 설정한 한도에 도달했는지. 실제 차단 여부와 다름 |
| quotaEnforced | 서버 차단 기능의 활성화 여부 |
| usageAvailable | 기록 누락·만료된 요청의 불확실성이 없는지 |
| usageBlocked | 한도 기능이 켜진 상태에서 불확실성 때문에 새 요청이 막혔는지 |
| resetsAt | 현재 사용량 집계 기간 종료 시각. periodEnd와 동일 |

한도 미설정은 무제한 상품을 확정했다는 뜻이 아니다. 현재 RAG가 usage를 누락하면
기존 기록 합계는 전체 소비량을 나타내지 않는다. usageAvailable=false도 함께 표시한다.

| HTTP / code | 프론트 동작 |
| --- | --- |
| 429 MEMBER_TOKEN_LIMIT_EXCEEDED | 사용량 재조회, 기간 종료/요금제 안내. 같은 새 요청을 자동 반복하지 않음 |
| 409 MEMBER_REQUEST_IN_PROGRESS | 진행 중 요청 완료 대기. 그 후 동일 요청 ID로 결과 확인 |
| 503 MEMBER_USAGE_UNAVAILABLE | 사용량 확인 필요 안내. 자동 재결제나 무한 요청 재시도 금지 |

## 정확한 차단 범위

토큰은 AI 실행 후 확정된다. 호출 전 사용량이 한도 미만이면 이번 요청은 허용하고,
이번 요청이 한도를 넘기면 결과를 보존한 후 다음 새 호출부터 차단한다. 출력까지
정확히 상한에 맞추는 방식이나 공급자 비용 상한을 보장하는 방식은 아니다.

회원별 DB lease가 AI 호출부터 사용량 기록·대화 저장까지 한 요청을 보호한다.
저장된 결과 재조회는 한도 검사보다 먼저 처리하므로 한도 도달·사용량 확인 중에도
가능하다. 진행 중 요청이 있는 동안에는 같은 회원의 다른 요청도 409를 반환한다.
한 JVM의 메모리 잠금에 의존하지 않아 여러 서버에서도 같은 DB로 조정한다.

lease의 유효기간은 RAG 대기 시간 + 2분이다. 서버 장애 시 만료 후 회수하며,
소비량이 불분명하므로 usageUncertain을 보존한다. 한도 기능이 켜져 있으면 새 AI
호출을 막고, 꺼져 있으면 호환성을 유지한다. 매우 긴 DB 정지·네트워크 장애·만료한
작업자의 지연 완료까지 무조건 단일 실행을 보장하는 분산 fencing 기능은 아니다.
서로 다른 requestId 및 이미 소비한 공급자 호출은 회원 집계의 멱등성과 구분한다.

usage 누락/0/잘못된 값이면 성공 답변은 저장하되 lease에 불확실성을 남긴다.
서버 재시작이나 기간 변경만으로 이를 삭제하지 않는다. 기록 저장 실패도 표시한다.
공급자 오류·타임아웃 이전에 실제 발생한 비용은 기존 회원 성공 요청 집계의 범위 밖이며,
별도 운영 비용 원장이 필요하다. 관련 정책은 아직 팀의 결정 대상이다.

## 점검·복구

1. 운영 SQL로 usageUncertain 및 만료 lease를 확인한다.
2. 해당 배포의 RAG 계약·사용량 저장 실패를 해결한다.
3. 공급자 측 실제 기록과 requestId를 확인한다. 로그에 프롬프트·토큰·키를 복사하지 않는다.
4. 실제 토큰을 확인할 수 있을 때 기존 기록 API 로직으로 중복 없이 보정한다.
5. 진행 중 작업이 없고 누락 소비가 해결됐다는 증거가 있을 때만 DB 관리 절차로
   해당 회원의 usage_uncertain을 해제한다. 자동 해제나 임의 0토큰 보정은 제공하지 않는다.

staging의 ddl-auto=update는 새 테이블을 생성한다. 스키마 관리 환경은
`backend/db/manual/20261006-member-request-lease.sql`을 복구된 DB 복사본에서 검증 후 적용한다.
전체 Flyway 도입은 기존 DB 스키마 실측과 baseline 설계 후 진행한다.
