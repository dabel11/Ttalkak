# TTALKAK 스테이징 승인형 사용자 시나리오 검증 계획

> 준비 문서 (실행/통과 결과가 아님). 2026-10-19.
> 현재 테스트 환경은 Railway 프로젝트 `ttalkak-staging`의 production 환경이다.
> 사용자에게 실제 데이터 및 API 비용이 발생할 수 있으므로 **승인된 별도 테스트 계정/실행 범위가 마련되기 전에는 쓰기 요청을 수행하지 않는다.**

## 1. 사전 준비 및 안전 범위

- Railway의 `web`/`backend`/`rag-server`/`MySQL`가 정상 상태인지 확인한다.
- 공개 GET/OPTIONS는 `.github/workflows/staging-readonly-acceptance.yml`에서 정기적/수동으로 재검증할 수 있다. 이 검증은 **실제 AI 생성 성공의 증거가 아니다.**
- 테스트 담당자와 **서로 다른 두 계정(A, B)** 을 격리해 마련한다. 기존 실사용자/상용 계정은 사용하지 않는다.
- 팀원 혹은 프로젝트 소유자에게 시험 중 계정 생성·작성·AI 호출 비용의 범위를 사전에 승인받는다.
- 비밀값·이메일 주소·토큰·사용자 입력 원문은 GitHub PR/이슈, CI 로그, 공유 스크린샷에 기록하지 않는다. 토큰을 URL 또는 CLI 인수로 전달하지 않는다.
- 개인정보 공개 게시글은 테스트 전용 합성 문장만 사용한다. 실제 회원 이름/연락처/거래 기록 사용 금지.
- 실결제/자동갱신/환불·관리자 권한 변경 및 운영 DB 복원은 **범위 제외**. `BILLING_MODE`를 변경하지 않는다.
- 무료/유료 모델 비용의 승인된 상한과 시험 호출 수를 문서화한다. 별도 합의가 없으면 실제 RAG 개선 요청은 실행하지 않는다.

## 2. 스모크 실행표 (승인 후에만)

| 순서 | 단계 | 합격 기준 | 영향/정리 |
| --- | --- | --- | --- |
| RO-01 | 공개 `/healthz`, `/api/tags/popular`, `/api/auth/config` | 200, JSON 및 공개 설정 필드 정상 | 읽기 전용 |
| RO-02 | 무인증 회원·관리자 GET, 허용되지 않은 웹·확장 Origin OPTIONS | 401 또는 403, CORS Origin 반사 없음 | 읽기 전용 |
| ID-01 | 테스트 A·B 계정 로그인/재로그인 | 본인 프로필만 보임, 타 계정 JWT 혼선 없음 | 세션 발급 |
| ID-02 | A/B 폴더·대화 생성 및 교차 조회 | A의 ID로 B가 GET/PATCH/DELETE 불가; B의 ID로 A도 동일 | 테스트 객체만 사후 정리 |
| PR-01 | A가 합성 게시글 공유, B가 저장/좋아요/댓글·신고 | 본인 기록만, 게시글·댓글·신고 상태는 기대 규약 충족 | 테스트 글/댓글/신고 생성 |
| PR-02 | A가 게시글 비공개 전환 후 B 목록·신고 기록 재조회 | B의 `/api/prompts/my`, `/api/me/library`, `/api/me/comments`, `/api/me/reports`에서 원문/제목 미노출; 접근 불가 신고 생성 거부 | **PR #69 패치 배포 후에만 기대 결과 검증** |
| AI-01 | 사전 합의한 소량의 개선 요청, 개선 결과 저장 및 재조회 | 응답 성공/실패 정책, requestId 멱등, `/api/me/usage` 중복 차감 없음 | 실제 AI 비용 가능, 허가 전 미실행 |
| AU-01 | 테스트 계정 일반/관리자 권한 차단 | 위조 역할/타 회원 데이터 수정 불가 | 위험한 관리자 작업·실운영 계정 테스트 금지 |
| RE-01 | 로그아웃 및 토큰 무효화 | 로그아웃된 JWT로 민감 API 401 | 테스트 토큰 종료 |

### 특히 주의

- ID-02/PR-01/PR-02는 실제 운영 DB에 **쓰기를 수행**한다. 읽기 전용 검사와 섞지 않는다.
- PR-02의 패치는 현재 Draft PR #69에 있으므로 해당 PR을 병합·배포하기 전 운영 웹에서 이 테스트를 수행하면 비공개 데이터 노출 여부를 다시 확인해야 한다. 실제 개인정보는 절대 사용하지 않는다.
- 기존 기록을 테스트로 생성할 경우 **삭제/비공개 처리가 완전한 DB 삭제를 뜻하지 않는다**. 테스트 데이터 보존 및 정리 정책을 사전에 협의한다.
- Google 로그인·비밀번호 복구 메일의 최종 검증은 연결된 외부 공급자와 테스트용 메일 수신을 따로 확인해야 한다.

## 3. 기록 형식과 완료 조건

각 항목마다 `TEST_ID | KST 실행 시각 | web/backend/rag 배포 커밋 | 익명 테스트 계정 별칭 | 예상 응답 | 실제 응답 코드 | PASS/FAIL/SKIP | 관련 이슈`만 남긴다.
보안 실패가 발생하면 공개 이슈에 응답 본문 전체·대상 ID/비밀값을 첨부하지 말고, 제한된 경로에서 최소 재현 증거를 관리한다.

최종 졸업프로젝트 통과 판정은 기능 CI, 실제 승인된 테스트 계정 E2E, AI 품질 평가의 사람 판정 근거, 격리 DB 복원 결과의 범위를 구분해 작성한다. 운영용 MySQL 9의 실제 복구 테스트 및 사업화 결제 인수인계는 이 문서에서 **SKIP/미완료**로 유지한다.
