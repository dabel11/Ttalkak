# TTALKAK 서비스 장애 및 데이터 복구 대응 절차

> 2026-10-19 · 학기 최종 검수용 운영 가이드 (실제 장애 복구 완료 기록 아님)
> 대상: Railway `ttalkak-staging` 및 추후 분리할 상용 운영 환경.
> **운영 DB/결제/비밀 변수 조정은 담당자 확인 및 복구 가능성 확보 이전에 진행하지 않는다.**

## 1. 서비스별 기본 분류

| 증상 | 우선 점검 | 예외/주의 |
| --- | --- | --- |
| 전체 페이지 5xx/빈 화면 | web 배포 상태, nginx 컨테이너 로그, 정적 파일 `/healthz` | `/healthz=200`만으로 API/RAG 정상이라고 판단하지 않음 |
| API 5xx·접속 불가 | backend 배포 상태, 로그의 예외 유형, MySQL 연결 상태 | 요청 본문·JWT·비밀번호·키를 티켓에 기재하지 않음 |
| 개선 요청만 실패/지연 | rag-server 배포 상태, 내부 `/health` 기동, RAG 응답 타임아웃(기본 75s), 공급자 장애/할당량 | AI 파이프라인 수정은 AI 담당자와 협의 |
| 로그인/복구 오류 | `/api/auth/config`, 실제 인증 공급자 및 메일 전송, 응답 코드(401/429/503), 요청 제한 | 계정 존재 여부 노출/메일 발송 성공을 원격 공개 GET만으로 단정하지 않음 |
| AI 사용량 누락 | 사용자 `/api/me/usage`의 `usageAvailable`, `usageBlocked`, 중복 요청/리플레이 기록 | 집계 불확실성일 때 무료 이용권·차감값을 임의로 복원하지 않음 |
| 테스트 결제 PENDING/실패 | `BILLING_MODE` 활성화 여부, 주문 ID/멱등 키, 공급자 기존 주문 조회 | **재결제·새 결제 시도 금지**. 라이브 결제 기본 비활성 유지 |
| 데이터베이스 용량/스키마 문제 | MySQL 상태/볼륨 사용량/백업 시각/최근 schema 변경 | 볼륨 삭제, production DB에 test dump 복원, JPA ddl-auto 변경 금지 |

## 2. 점검 우선순위와 증거

1. 장애 시작/종료 시각, 영향받는 서비스·기능, 배포 커밋·환경을 식별한다. 원인을 단정하지 않는다.
2. Railway 각 서비스 상태·에러율·최근 배포 로그를 확인한다. 오래된 502 기록은 현재 장애와 구분한다.
3. **읽기 전용** 공개 검사: `python3 scripts/check-staging-readiness.py --origin https://web-production-a82d94.up.railway.app --security` (현재 `develop`에 있음). `GET/OPTIONS`만 수행하고 자격 증명은 보내지 않는다.
4. 반복 재현은 별도 `ttalkak-ci` 테스트 DB, Spring, RAG fixture를 사용한다. 실제 AI 호출/메일 발송/결제/게시글 생성은 이 진단의 일부가 아니다.
5. 서비스 안정성에 문제가 있다면 우선 변경 중단, 최근 정상 배포·설정/스키마 호환성 확인, 관리자/담당자와 롤백 범위 협의. **DB 스키마를 과거 상태로 되돌리거나 데이터 삭제로 임시 해결하지 않는다.**
6. 해결 후 공개 검사, 격리 통합 테스트, 승인된 테스트 계정 E2E 순서로 다시 확인한다.

## 3. 스키마 변경 보호 게이트

- 현재 저장소의 `backend/src/main/resources/application.yml`은 `JPA_DDL_AUTO`가 없으면 `update`로 설정된다. 실제 Railway 환경변수 값은 **별도 확인이 필요**하며, 설정값을 추정하지 않는다.
- 운영 MySQL 인스턴스에 Flyway/Liquibase baseline을 바로 반영하지 않는다. 실제 `information_schema`와 엔티티 차이 분석 및 별도 데이터 복원 연습을 선행한다.
- 백업본을 먼저 확보하고 **독립된 격리 DB**에서 복원·테이블/행수/컬럼 정의/인덱스/제약조건을 비교한다. `scripts/check-disposable-db-restore.sh`는 **MySQL 8.4 테스트용**이며 운영 MySQL 9의 복구 성공을 보장하지 않는다.
- CI 테스트가 완수되어도 운영 DB의 주기적 외부 백업, 접근 권한, 키 관리, RPO/RTO 및 실제 운영 MySQL 버전 복원 검증은 별도 작업으로 남는다.

## 4. 인증·권한 보안 운영 확인

- 토큰은 JWT 서명과 issuer/만료, DB의 계정 상태·권한·인증 버전, 명시적 해지 목록으로 검증해야 한다. 클라이언트 제공 `role`/ID만으로 관리자 권한을 부여하지 않는다.
- 로그인·계정 복구 rate-limit은 **현재 단일 애플리케이션 프로세스 메모리 기준**이다. 서버 재시작·수평 확장·실제 프록시 IP 전달 상태에 대한 운영 검증 전에는 분산형 방어를 완료했다고 표현하지 않는다.
- 권한 회귀 테스트에는 공개/비공개 게시글뿐 아니라 타 사용자 `/api/make/threads`·폴더·관리자 API를 포함한다.
- OAuth/메일 공급자 활성화 플래그는 인증/실제 이메일 도착까지 증명하지 않으므로 별도 승인된 테스트 계정으로 확인한다.

## 5. 사고 기록 최소 항목

`시작(KST) | 영향 범위 | 재현 환경 | 최초 응답 코드 | 최근 배포/커밋 | 진단 근거 | 완화 조치 | 복구 후 검증 | 후속 이슈`

실제 사용자의 대화·이메일·전화번호·비밀번호·JWT·키·토스 주문/결제 비밀을 GitHub 이슈 또는 공유 로그에 저장하지 않는다. 민감정보 유출이 의심되면 노출 범위·권한 통제와 비밀값 교체/세션 무효화 등을 우선 검토한다.

## 6. 협업·사업화 분리

졸업프로젝트 완료 전에는 읽기 전용 점검과 폐기 가능한 CI 검증을 우선한다. 배포 환경 변경·실운영 데이터 복원·상용 PG 결제/환불 활성화는 졸업프로젝트의 기본 완료 조건에 포함하지 않는다. 사업화 전 개인정보·계정/서비스 운영자 권한·문의/환불·장애 대응 의사결정 책임을 별도 합의한다.
