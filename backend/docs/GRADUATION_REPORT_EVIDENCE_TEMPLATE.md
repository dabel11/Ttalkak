# TTALKAK 졸업프로젝트 결과보고서 증빙 템플릿

> 실제 실험·배포에서 확인된 내용만 기입한다. **미확인/미완료 칸은 공란으로 두지 말고 명시한다.**
> 이 문서는 검증 결과를 새로 생성하지 않으며, 인증정보·사용자 대화·결제정보를 보관하지 않는다.

## 1. 프로젝트 소개

- **서비스 목적:** 사용자 의도를 유지하면서 AI 프롬프트의 명확성·실행 가능성을 개선하고, 부족한 정보는 사용자에게 질문한다.
- **구성:** Web/Extension → Spring Boot API → FastAPI/RAG·LLM → 응답 및 저장/재조회
- **팀 업무 범위:** PM·백엔드·통합 / 프론트엔드·확장 프로그램 / AI·RAG의 최신 기여도는 실제 GitHub 커밋 및 팀 확인으로 정리한다.
- **평가 가설:** 개선된 프롬프트가 사용자 요구를 충족하는 최종 생성 결과의 품질을 개선하며, 충분히 명확한 요청을 불필요하게 악화시키지 않는다.

| Track B / TTALKAK | 동일 | 미집계 | 미집계 | 미집계 | 미집계 | 동일 조건 확인 | 미완료 |

- Track A는 **유지/악화 방지**, Track B는 **유용성 개선**이라는 목표와 평가 방법이 다르므로 단순 평균으로 섞지 않는다.
- LLM Judge 점수와 사람 평가 사이의 일치도가 검증되지 않았다면 해당 숫자를 최종 결론으로 사용하지 않는다.
- 기존 과거 파일에는 Track A 31문항 중 9개 항목의 raw·TTALKAK 비교 기록이 있다. 31문항 전체의 완료/승률로 환산하지 않는다.
- RAG 검색 품질 지표와 결과물 품질 지표를 따로 기록한다. 비용, 타임아웃, 호출 실패까지 함께 기재한다.

## 5. 보고서에 사용 가능한 결론 표현 기준

- **가능:** “독립된 테스트 데이터베이스에서 인증 및 저장 동작을 재현했다.” 단, 해당 CI 실행 결과를 첨부할 것.
- **가능:** “공개 스테이징 API의 기본 응답 및 비인가 접근 제한을 확인했다.” GET/OPTIONS 검증 범위 한정.
- **조건부:** “프롬프트 개선으로 결과물의 충실도가 향상됐다.” 동일 조건 A/B 실험 및 판정기/사람 검증 근거가 있을 때만.
- **불가:** “실제 사용자 전원의 기능이 검증됐다”, “운영 MySQL 백업 복원이 성공했다”, “상용 결제가 준비됐다” — 근거 부족.

## 6. 담당자에게 최종 확인할 최소 항목

백엔드/PM은 병합·배포 SHA와 사용자 흐름, AI 담당자는 실험 기록·동일 조건·평가 한계, 프론트 담당자는 실제 웹/확장 흐름·시연 안정성을 확인한다. 팀원 확인이 필요한 항목은 시험기간 이후에 **한 번에** 요청한다.
