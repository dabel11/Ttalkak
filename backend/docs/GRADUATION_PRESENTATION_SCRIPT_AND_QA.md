# TTALKAK 졸업프로젝트 최종 발표 대본 및 질의응답

> **발표 리허설 초안 / 목표 5분.** 시연 시간·속도는 리허설에서 조정한다.
> 공개 배포 건강 검증(읽기 전용), CI 테스트, 실제 AI 개선 효과, 사람 평가를 혼동하지 않는다.
> 합성 시연 예시는 [데모 카드](GRADUATION_DEMO_CASES.md)에서 선택하고, 실제 결과는 확인 후만 언급한다.

## 0:00–0:45 프로젝트 배경·핵심 가치

안녕하세요. 저희 팀은 AI에게 원하는 내용을 정확하게 요청하는 과정을 도와주는 프롬프트 개선 서비스, **TTALKAK, 딸깍**을 개발했습니다.

생성형 AI는 누구나 사용할 수 있지만, 좋은 결과를 얻으려면 목적과 상황을 명확하게 전달해야 합니다. 사용자가 무엇을 요청해야 할지 잘 모르거나 필요한 조건을 빠뜨린 경우가 있다는 점에서 출발했습니다.

저희 서비스의 핵심은 문장을 무조건 길게 만드는 것이 아니라, **사용자의 의도를 보존하면서 필요한 정보를 구조화하고, 정보가 부족하면 임의로 채우기보다 질문하는 것**입니다.

## 0:45–1:35 시스템 구조

사용자는 웹 또는 Chrome 확장 프로그램에서 원래 요청을 입력합니다. 요청은 Spring Boot 백엔드를 거쳐 FastAPI 기반 AI 서버로 전달됩니다.

AI 서버는 검색 기반 정보를 참고해 개선 프롬프트와 필요할 경우 추가 질문을 구성하고, 결과는 다시 백엔드를 통해 사용자 화면으로 전달됩니다. 로그인 사용자는 개선 내역과 프롬프트를 저장해 다시 사용할 수 있습니다.

또한 비회원 체험, 회원 인증, 커뮤니티, 사용량 관리, 중복 요청 처리 등의 기능을 백엔드에서 관리하도록 구성했습니다.

## 1:35–3:10 시연 (화면 진행)

**화면 A — 주제와 작업이 명확한 요청:** 가상 도서관의 독서모임 홍보 문구를 입력합니다. 조건이 충분하면 바로 개선안을 제공하는지, 날짜·대상·형식이 유지되는지, 아직 정해지지 않은 참가비나 신청 링크를 임의로 만들지 않는지 확인합니다.

**화면 B — 정보가 부족한 요청:** “안내문 작성해줘”처럼 주제가 없는 요청을 입력해 임의로 사실을 지정하기보다 추가 정보를 질문하도록 설계한 흐름을 설명합니다.

**화면 C — 후속 입력:** 같은 대화에 말투 변경 조건을 추가하고, 이전에 제공한 제약이 유지되는지 확인합니다. 승인된 테스트 계정으로 검증한 경우에만 저장·재로그인·재조회 결과까지 시연합니다.

*이 문구는 시연 진행 안내입니다. 각 기능의 실서버 실행 결과를 실제로 확인하기 전에는 “성공했습니다”라고 말하지 않습니다. 실패하면 가려진 사실 없이 [대체 시연 절차](GRADUATION_FINAL_DEMO.md)를 따릅니다.*

## 3:10–4:15 검증 방법과 현재 한계

기능의 동작은 먼저 Spring Boot, MySQL, 프론트엔드, 모의 AI 서버를 연결한 격리된 CI 환경에서 검사했습니다. 여기에는 로그인·사용량 제한, 데이터 저장과 재조회, 접근 권한, 재시작 후 데이터 지속성 등이 포함됩니다.

실제 배포 사이트에 대해서는 공개 API 상태와 비인가 접근 제한을 읽기 전용으로 확인했습니다. 다만 이것만으로 실제 AI 공급자의 모든 요청이나 사용자 흐름이 검증됐다고 해석하지 않습니다.

**효과 검증은 별도 단계입니다.** 이미 마련된 평가셋은 48항목이며, 조건이 충분한 요청에서 성능이 나빠지지 않는지와 조건이 부족한 요청에서 실제 도움이 되는지를 나누어 평가합니다. 사람의 독립 판정과 충분한 비교 결과를 확보하지 않은 성능 수치는 최종 결론으로 주장하지 않겠습니다.

## 4:15–5:00 팀 기여와 결론

팀은 **기획·PM/백엔드, 프론트엔드/확장 프로그램, AI/RAG**로 역할을 나누었습니다.

저는 전체 사용자 흐름과 요구사항을 조율하고 백엔드 API, 인증·사용량·커뮤니티, 통합 및 배포 검증을 담당했습니다. 프론트엔드 담당자는 웹과 확장 프로그램의 실제 입력·개선·저장 사용자 경험을 구현했고, AI 담당자는 검색과 생성 파이프라인, 개선 프롬프트 생성 및 품질 평가 체계를 구축했습니다.

TTALKAK이 전하려는 가치는 단순한 프롬프트 자동 완성이 아니라 **사용자가 AI에 자신의 의도를 정확히 전달하도록 돕는 것**입니다. 남은 검증 결과와 한계도 투명하게 기록해 프로젝트를 완성하겠습니다. 감사합니다.

## 교수님 예상 질문과 답변 가이드

| 질문 | 근거 있는 답변 방향 |
| --- | --- |
| ChatGPT에 직접 프롬프트를 고쳐 달라고 하면 되지 않나요? | 사용자는 어떤 조건을 제공해야 할지도 모를 수 있습니다. TTALKAK은 개선·추가 질문·저장/재사용을 일관된 사용자 흐름으로 제공합니다. **우월성은 비교 실험으로 입증해야 합니다.** |
| RAG가 정말 결과를 좋게 만들었나요? | RAG 도입 자체로 효과를 단정하지 않습니다. 동일 입력의 RAG on/off, 이상적 근거 조건을 비교하는 평가 체계가 있고, 완료된 사례의 이득·방해를 구분할 계획입니다. |
| 환각이 줄었다고 어떻게 증명하나요? | 정보가 없는 사실을 마음대로 채우지 않고 질문하는 설계가 있지만, 실제 감소 효과는 고정 사례 및 사람 판정·결함 라벨 검증으로 측정해야 합니다. |
| 실제 배포가 완료됐나요? | 웹·백엔드·RAG·DB 서비스 가동 상태와 공개 API 접근 검사를 확인했습니다. 로그인→실제 LLM→저장 등 **실환경 전체 E2E는 별도 확인이 필요한 범위**입니다. |
| 개인정보와 보안은 어떻게 처리했나요? | 계정 접근과 타 회원 데이터 분리, 비공개 콘텐츠 노출 관련 회귀 테스트를 추가했습니다. 현재 보안 수정은 [Draft PR #69](https://github.com/dabel11/Ttalkak/pull/69)에 있어 실제 서비스 반영과 추가 검증이 필요합니다. |
| 유료 서비스로 바로 운영할 수 있나요? | 졸업프로젝트와 사업화를 분리했습니다. 운영 DB 복구, 개인정보 보존·파기, PG 라이브 결제·환불/고객지원은 추가 검증 및 정책 확정 이후 진행합니다. |
| 세 팀원의 기여도는 어떻게 구분하나요? | PM/백엔드는 요구사항·API·통합, 프론트 담당자는 웹/확장 UX, AI 담당자는 검색·생성·평가로 구분합니다. 기여 시점과 범위는 최종 병합 기록으로 확인합니다. |

## 리허설 전 최종 검토

- [ ] `develop`에 병합된 기능과 Draft PR 기능을 명확하게 구분
- [ ] 실제 AI 성능표와 사람 판정 결과가 없으면 `미완료`로 표시
- [ ] 로컬 테스트/CI 로그의 성공과 Railway 실서비스의 성공을 구분
- [ ] 웹/확장, AI, 백엔드 담당자별 최신 기여도 표현 확인
- [ ] 시연 화면에 로그인 토큰·계정 개인정보·결제 정보가 나타나지 않도록 점검
