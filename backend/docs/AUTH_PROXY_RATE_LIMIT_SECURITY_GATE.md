# 인증 요청 제한 — 신뢰 경계·검증·운영 게이트

## 취약 원인
- 기존 `AuthRateLimitFilter`는 `getRemoteAddr()`를 신뢰했다. `FORWARD_HEADERS_STRATEGY=framework`일 때 Spring `ForwardedHeaderFilter`가 감싼 요청의 원격 주소는 클라이언트가 전달한 `Forwarded` 또는 `X-Forwarded-For`의 영향을 받을 수 있다.
- 기존 nginx는 `$proxy_add_x_forwarded_for`로 기존 XFF에 값을 추가했다. 신뢰되지 않은 XFF를 백엔드 제한 키에 사용하는 것은 위험하다.
- 10,000개의 `IP:경로` 윈도가 포화되면 처음 보는 주소는 429를 받는다. 무분별한 퇴거나 전역 공유 제한은 기존 카운터 초기화·정상 사용자 차단이라는 새 문제를 만든다.

## 이 PR에서 적용한 코드 수정
1. 인증 필터는 ForwardedHeaderFilter의 바깥 래퍼가 제공한 주소 대신 **가장 안쪽 servlet 요청의 socket peer 주소**를 기본값으로 사용한다. 위조된 XFF만 바꿔서는 제한 키가 바뀌지 않는다.
2. 실제 사용자별 IP가 필요한 nginx 내부 경로는 `TTALKAK_AUTH_PROXY_SECRET`이라는 별도 무작위 32자 이상 비밀값으로 **내부 프록시의 전달을 인증할 때만** `X-Ttalkak-Client-IP` 주소를 사용한다. 인증 실패·비활성·잘못된 IP는 socket peer로 돌아간다.
3. `TTALKAK_AUTH_PROXY_REQUIRED=true`를 선택한 경우, 인증된 프록시 헤더가 없거나 유효하지 않은 인증 POST 요청은 컨트롤러로 전달하지 않고 503을 반환한다. 이 설정은 기존 백엔드 직통 클라이언트를 깨뜨릴 수 있어 전환 후에만 켜야 한다. 설정이 true인데 비밀값이 비어 있거나 약하면 서버 기동 자체를 거부한다.
4. nginx는 외부 XFF를 이어붙이지 않으며, Railway **공개 HTTP 엣지가 덮어쓰는** `X-Real-IP` 값을 XFF와 내부 인증 클라이언트 IP에 사용한다. 표준 `Forwarded` 헤더도 제거한다.
5. 현재 구현은 12개 5초 버킷의 고정 크기 스케치로 10,000개 키 상한을 대체한다. 복구 10회·그 외 30회의 한도를 적용하지만 최대 약 5초 조기 해제와 충돌 오차단 가능성이 있다. 예전 map의 주기적 키 정리 방식은 사용하지 않는다. 아래 후속 기록에는 교체된 과거 구현도 포함되어 있으므로 최종 5초 버킷 기록을 기준으로 판단한다.

## Railway 실제 구성에서 확인한 제약 (2026-10-27, 읽기 전용)
- 같은 `ttalkak-staging` Railway 프로젝트의 **web과 backend 양쪽에 각각 공개 도메인**이 있고, 서비스는 `develop` 브랜치 1개 복제본으로 동작한다.
- web→nginx→backend 사설 연결과 backend 공개 주소 직접 접근이 함께 가능하다. **backend 직접 접근은 내부 nginx의 프록시 비밀값을 받지 않으므로 socket peer fallback을 사용한다.** 이 경우 공개 엣지의 다수 사용자 요청이 같은 프록시 IP로 보이면 잘못된 429가 발생할 수 있다.
- Railway 공개 HTTP 엣지는 `X-Real-IP`를 덮어쓴다고 안내한다. 단, `*.railway.internal` 사설 네트워크 또는 TCP 프록시 경로에서는 해당 보장이 적용되지 않는다. **사설 네트워크를 통한 nginx 직접 접근이 가능하면 공격자가 X-Real-IP를 위조할 위험이 있으므로, 내부 서비스 호출자 신뢰 범위와 연결 경로를 검증해야 한다.**
- Railway 공개 도메인을 통한 backend 직접 경로와 웹·확장 프로그램의 기존 API 호출 의존성을 조사하고, **하나의 신뢰된 공개 ingress로 경로를 통합하기 전에는 보안을 완료 처리하지 않는다.** 공개 backend 도메인을 임의로 제거하면 확장 프로그램 호출이 깨질 수 있으므로 담당자와 통합 테스트 후 변경한다.

## 환경변수 설정 게이트 (현재 운영에 적용하지 않음)
- web nginx와 backend 양쪽에 동일한 **URL-safe 영숫자·`_`·`-`만 포함하는 무작위 32자 이상** 비밀값 `TTALKAK_AUTH_PROXY_SECRET`을 별도 주입한다. nginx 템플릿 주입 위험을 막기 위해 허용 문자 검증을 적용한다. 저장소·PR·메신저에 실제 값을 남기지 않는다.
- nginx 템플릿의 환경변수 치환 방식이 `TTALKAK_AUTH_PROXY_SECRET`을 정상 치환하는지 격리 컨테이너에서 검증한다. 비밀값이 누락되면 백엔드는 socket peer를 사용하므로 헤더 위조를 신뢰하지 않는다.
- `FORWARD_HEADERS_STRATEGY`가 `framework`가 아닌 `native` 등으로 바뀌면 서블릿 원본 주소에도 영향을 줄 수 있으므로 **현재 확인된 설정의 변경을 별도 검토**한다.
- 백엔드 직통 공개 도메인과 확장 프로그램·외부 API 호출이 모두 웹 프록시 경로로 이전했음을 확인한 뒤 `TTALKAK_AUTH_PROXY_REQUIRED=true`를 승인된 배포 시점에 적용한다. 엄격 모드에서는 백엔드 직통 인증 POST가 503으로 거부된다.
- 비밀값이 적용된 상태의 nginx 직접 사설 경로는 신뢰된 서비스만 접근 가능한지 검증한다. 비밀값을 보유한 nginx가 신뢰되지 않은 X-Real-IP를 그대로 전달한다면 내부 인증만으로 사용자 IP 진위가 증명되지 않는다.

## 릴리스 판정
**Draft / 운영 배포 차단.** 본 PR은 코드 수준의 XFF 스푸핑 방어를 추가하지만, Railway 실제 ingress 통합·비운영 E2E·인증 비밀 설정·다중 인스턴스 문제까지 해결됐다는 의미는 아니다. 공개 도메인 삭제, 환경변수 변경, 실제 서비스 배포, DB 변경·병합은 별도 사용자 승인 없이 수행하지 않는다.

## 자동화된 격리 종단간 검사
- `docker/compose.auth-proxy-ci.yml`은 기존 disposable Compose 스택에서 **백엔드 strict 프록시 모드** 및 웹 nginx/백엔드 공유 **테스트 전용 비밀값**을 적용한다. 실제 Railway 변수나 사용자 DB는 사용하지 않는다.
- `scripts/check-disposable-auth-proxy.py`는 실제 nginx → Spring을 통해 가짜 XFF/RFC Forwarded/가짜 프록시 비밀 헤더가 덮어써지는지, 동일한 검증된 IP의 11번째 아이디 찾기 요청이 429인지, 다른 검증된 IP는 별도 제한을 갖는지 확인한다.
- 또 다른 컨테이너에서 backend 사설 주소로 직접 전송한 미인증 인증 요청이 strict 모드에서 **503 AUTH_PROXY_REQUIRED**로 거부되는지 검증한다.
- 해당 테스트는 호스트에서 보내는 `X-Real-IP`로 Railway 공개 엣지가 부여한 값을 **모의**한다. Railway 엣지의 실제 재작성 보장이나 다른 서비스가 nginx 사설 주소로 접근하는 위험까지 자동 증명하지는 않는다.
- CI에서 기존 전체 disposable 게스트/회원/DB 검사 후 별도 strict 프록시 E2E를 수행하도록 설정했다. 결과가 확인되기 전에는 통과로 표시하지 않는다.

## 만료 경계·포화 시 성능 보강
- 제한 키 10,000개가 꽉 찬 경우 새 요청을 즉시 429 처리하기 전에 만료 항목 회수를 시도한다.
- 공격자가 신규 IP를 초당 대량 생성할 때마다 전체 10,000개 맵을 순회하는 CPU 고갈을 방지하기 위해, **포화 상태 전체 스캔은 최대 250ms 간격**으로 제한한다. 만료 직후 최대 약 250ms 동안 신규 키가 429를 받을 수 있으며 이 한계는 명시적으로 남긴다.
- 기존 IP의 10/30회 제한과 만료 시각은 그대로 유지한다. 제한 키 상한 자체와 다중 인스턴스 간 제한 공유는 해결되지 않았으며, 신뢰된 단일 공개 진입 경로 전환 및 엣지/공유 저장소 보호를 운영 릴리스 게이트로 유지한다.

## 2026-10-27 키 공간 고갈 방지 변경
- 기존 `Map<IP:경로, Window>` 및 10,000개 키 상한을 **4행 × 65,536 슬롯의 보수적 카운트-민 스케치**로 교체했다. 상태 저장 공간은 주소 개수와 무관하게 유한하며 신규 주소라는 이유만으로 전역 429를 반환하지 않는다.
- 각 요청은 고정된 4개 슬롯을 확인하고 그중 최소 카운트만 선택해 한도를 판정한다. 선택된 최소 카운트와 동일한 슬롯만 증가시키는 conservative update를 사용해 충돌 영향이 확대되는 것을 완화한다.
- 서로 다른 20,000개 공격성 주소를 섞어도 기존 정상 주소의 할당량이 유지되고 신규 정상 주소를 즉시 차단하지 않는 테스트, 제한된 주소가 다른 주소 유입으로 카운터를 초기화할 수 없는지 검사하는 테스트를 추가했다.
- **한계:** 유한 카운터에 서로 다른 주소가 많이 몰리면 해시 충돌에 의한 **오탐 429**가 가능하다. 실제 IP를 무한히 위조할 수 있는 진입 경로를 차단하는 프록시 신뢰 정책, 독립된 엣지 요청량 제한, 분산 환경의 상태 공유가 없는 한 모든 공격 패턴에서 정상 사용자 100% 허용을 보장할 수는 없다.
- 요청 제한은 단일 인스턴스에 적용되며, 서버 간 공유 한도는 구현되지 않았다. 60초 고정 상한과 스케치 충돌/재시작 시 동작을 추가 검증하고 CI 결과가 확정되기 전 완료로 선언하지 않는다.

## 키 공간 해시 충돌 방어
- Java `String.hashCode()`는 공격자가 충돌 문자열을 구성할 수 있으므로, 스케치 인덱싱에 사용하지 않는다. 필터 인스턴스 시작 시 생성한 무작위 256비트 비밀키를 사용하는 `HmacSHA256`으로 4개 독립 인덱스에 사용할 값을 생성한다.
- `Aa`와 `BB`처럼 기존 Java 해시가 같은 입력도 독립적인 사용자 제한을 갖는지 테스트한다.
- 이 변경은 사전 계획된 해시 충돌 유도를 어렵게 하지만, 스케치의 통계적 충돌과 많은 실제 공격 IP로 인한 오탐을 제거하는 것은 아니다.

## 스케치의 시간창 일관성 (2026-10-27)
- 개별 스케치 슬롯마다 고유 시작 시각을 사용하는 구현은 일부 충돌 슬롯만 먼저 만료될 수 있어 보수적 최소값의 한도를 부정확하게 낮출 수 있다. 모든 슬롯을 `Math.floorDiv(now, 60_000L)`으로 계산된 동일한 **고정 60초 epoch**에 정렬했다.
- 새 회귀 테스트는 59,999ms 직전 제한 초과, 60,000ms 경계에서 새 윈도로 전환, 60,001ms 재차 제한 초과를 확인한다.
- **운영 보안 유의:** 고정 윈도는 경계 전후 단시간에 두 윈도의 요청량을 연속 소진하는 버스트를 허용할 수 있다. 이 변경이 슬라이딩 윈도나 토큰 버킷과 동등하다고 주장하지 않는다. 고위험 복구 엔드포인트의 지속적 남용 방지는 검증된 엣지·분산 제한 및 발송량 정책과 함께 검토해야 한다.

## 분 경계 버스트 완화 (2026-10-27)
- 단일 고정 60초 epoch의 경계에서 10+10회 연속 허용될 수 있는 문제를 줄이기 위해 **서로 30초 어긋난 두 개의 60초 스케치**에서 모두 요청 한도를 확인한다.
- 두 시간창 모두 여유가 있는 요청만 승인하고, 둘의 최소 카운터에 각각 반영한다. 한 시간창에서 거부될 때에는 카운터를 갱신하지 않는다.
- 시간 경계 59,900ms에 한도를 모두 사용했다면 60,000ms 새 정각에도 거부되며 90,000ms 두 시간창이 모두 바뀌면 다시 허용되는 회귀 테스트를 추가했다.
- 두 시간창 구성은 **정확한 슬라이딩 윈도가 아니다.** 기존 고정 윈도의 과도한 경계 버스트를 완화하지만, 더 보수적으로 정상 사용자를 차단할 수 있고 일부 다른 시점에서는 근접 버스트가 가능하다. 운영 트래픽에서 오탐·지연률을 평가하고 필요하면 정확한 엣지·분산 rate limit으로 교체해야 한다.

## 2026-10-27 재검토: 이중 고정 창의 실질 우회 교정
- 기존 30초 간격 이중 60초 창 방식은 29.9초에 10회 실행하고 60초에 다시 10회를 호출할 때, 두 창의 최소 카운터가 모두 초기화된 것으로 간주될 수 있다. 이는 정확한 60초 제한 보장이 아니므로 **제거했다**.
- 대신 최근 12개의 **5초 버킷**을 고정 크기 conservative sketch로 추적하고 합산하여 한도를 검증한다. 거부된 요청은 새 버킷을 증가시키지 않는다.
- 윈도 경계의 대량 버스트 허용 오차는 버킷 양자화에 따른 최대 약 5초까지 남는다. 완전한 요청별 정확한 60초 슬라이딩 로그와 동등하다고 주장하지 않는다.
- 저장 공간은 `12 × 4 × 65,536` 슬롯 참조 배열이며, 각 버킷은 epoch를 저장해 이전 회전의 요청 횟수가 재사용되지 않도록 한다. 기존 단일 스케치보다 메모리·CPU 비용이 증가하므로 CI 성능 확인이 필요하다.
- 29.9초 소진 후 30초/60초 차단 및 90초 복구, 59.9초 소진 후 60초/90초 차단 및 120초 복구 테스트로 회귀 확인한다.
