# 이메일 기반 아이디 복구 전환 계획 (검증 전 설계안)

## 목표 및 선택
- 사용자에게 공개된 화면에서 아이디 일부를 보여주는 레거시 `POST /api/auth/find-id` 대신, 등록 이메일로 결과를 발송하는 `POST /api/auth/id-recovery/request`를 공식 복구 경로로 채택한다.
- 레거시 API를 이번 작업에서 제거하거나 동작을 변경하지 않는다. 웹/확장 프로그램의 실제 전환은 각 담당자 코드 검토 및 호환성 테스트 후 별도 PR에서 수행한다.
- 운영 메일 설정·실제 메일 발송은 이번 작업에서 수행하지 않는다.

## 기존 구현에서 확인한 사실
- `PasswordResetDispatcher.recoverUserId`는 이름·이메일을 검증하고 비동기 작업을 수행한다. 메일 기능이 비활성화되면 요청을 거절한다.
- `PasswordResetService.recoverUserId`는 활성 LOCAL 계정의 동일 이름·이메일을 다건 조회하고 차단 계정을 제외한 뒤, 일치 ID들을 정렬하여 해당 등록 이메일에 발송한다.
- `PasswordResetMailer.sendUserId`는 이메일로 아이디를 전달하며, 테스트 수신자 제한이 설정된 경우 다른 주소로 리다이렉트하지 않는다.
- 이 과정에 별도 일회용 이메일 소유권 검증 링크/코드는 없다. 다만 공개 HTTP 응답 대신 등록 이메일로 결과를 전달한다.
- 이름/연락처의 유일성 보장은 없다. 레거시 다중 일치 500 오류 방지는 별도 PR #79에서 다룬다.

## 개인정보 및 복구 정책
1. 성공적으로 접수된 정상 형식의 요청에는 대상 계정 존재 여부에 관계없이 동일한 공개 응답을 반환한다. 형식 오류, 서비스 미설정, 서버 측 rate limit은 별도로 취급한다.
2. 이름+이메일이 일치하는 활성·비차단 LOCAL 계정만 이메일 복구 대상이다. 탈퇴·차단·Google 계정은 목록에 넣지 않는다.
3. 여러 LOCAL ID가 매칭되면 공개 응답에는 어떠한 ID도 표시하지 않는다. 메일은 요청자가 입력한 등록 이메일로만 발송한다.
4. 메일/서버 로그에 이메일 주소, 원문 아이디, 인증 정보를 출력하지 않는다.
5. 악용 방지를 위해 동일 주소·IP·계정에 대한 발송 빈도, 메일 대량 발송, SMTP 오류와 계정 존재 노출 가능성을 별도 검토한다. 현재 제한 수준을 검증 없이 '완료'로 표시하지 않는다.
6. 클라이언트가 새 경로로 전환될 때까지 기존 API를 유지하고, 배포 후 전환 순서를 계획한다.

## 배포 전 필수 검증
- [ ] 유효한 요청의 공개 응답이 계정 존재 여부를 누설하지 않음
- [ ] 동일 이름/메일 0, 1, 2+ 계정의 발송 대상 및 반환 코드
- [ ] 차단·탈퇴·Google 혼재 시 등록 이메일 이외 수신자에게 발송되지 않음
- [ ] 발송 서비스 비활성·전송 실패·대기열 포화 시 안전한 오류 처리 및 민감정보 로그 비노출
- [ ] 반복 요청/동시 요청에 대한 abuse-rate 제한 검토
- [ ] 웹과 확장 프로그램의 전환 UX 및 기존 API 호환성 검토
- [ ] 실제 메일 설정은 비운영 격리 환경에서 별도 승인 후 시험

본 문서는 전환 설계와 검증 체크리스트이며, 사용자 인터페이스 전환이나 추가 인증코드 구현이 완료됐다는 의미가 아니다.


## 프론트엔드·확장 프로그램 후속 인계 (구현 금지: 담당자 협의 필요)
- 웹: `prompt-hub-web-frontend/src/auth/auth-controller.mjs`의 `find-id` 화면과 `src/api/auth-api.mjs`의 레거시 `findId` 호출을 점검한다.
- 확장: `extension/src/api/auth.js`의 `requestFindId` 호출을 점검한다.
- 공식 목표 API: `POST /api/auth/id-recovery/request` — 이름과 등록 이메일을 받아 메일 발송을 요청하며 공개 결과에 `maskedUserId`를 노출하지 않는다.
- UX: 요청 결과 화면은 계정 존재 여부와 관계없이 동일한 안내를 사용한다. Google 전용 계정은 별도 Google 로그인 안내를 노출하되 계정 존재 여부를 공개 API 응답으로 추론할 수 없도록 한다.
- 주의: 기존 레거시 API는 웹·확장 전환 완료 및 회귀 검증 전까지 삭제하지 않는다. 프론트 담당자가 기존 호출/응답 계약을 확인해야 한다.
- 클라이언트/통합 테스트: 정상 메일 전송 요청, 존재하지 않는 계정, 잘못된 이메일, 메일 미설정, 429 제한 응답, 화면 재시도, 기존 레거시 진입 및 신규 방식 전환을 검증한다.
- 웹/확장 코드 변경을 본 PR에 포함하지 않는다. 전환 일정과 사용자 안내 문구는 담당자와 별도 협의한다.

## 현재 백엔드 검증 구분
- `AuthRecoveryIntegrationTest`에서 이메일 다건 매칭, 차단·Google 계정 혼재 및 수신 대상 필터링 테스트를 추가했다.
- 이 회귀 테스트는 Mockito 메일 발송 검증으로 실제 SMTP/Resend 발송 성공을 증명하지 않는다.
- CI와 운영 메일 설정 및 서비스별 요청 제한·동시성 내성은 독립적으로 확인해야 한다.


## 2026-10-27 보안 재검토: 부적절한 쿨다운 제거
- 이름+이메일 기반 인메모리 쿨다운은 다른 이름으로 동일 주소 발송을 반복하는 공격을 막지 못하고, 저장 한도 고갈로 정상 복구를 거부할 수 있어 제거했다.
- 이메일 단독 쿨다운 역시 잘못된 이름으로 타인의 정상 복구를 선점하는 공격에 취약해 적용하지 않는다.
- 현재 확인 가능한 백엔드 방어는 입력 형식 검증과 크기가 제한된 비동기 발송 큐다. **큐 제한은 IP·수신자별 발송 횟수 제한을 대체하지 않는다.**
- 메일 발송 API의 공통 HTTP rate limiter 연결 여부, 프록시 IP 신뢰 경계, 다중 인스턴스의 공통 rate limit, 대량 요청 시 발송량 및 정상 사용자 영향은 별도로 검증해야 한다.
- 이 검증이 끝나기 전 실제 메일 서비스를 공개 운영 대상으로 활성화하거나 본 PR을 '이메일 발송 남용 방어 완료'로 설명하지 않는다.
- 테스트는 비정상 형식 입력 거부, 잘못된 이름의 요청이 정상 이름의 요청을 선점하지 않음, 다건 계정 필터링 및 메일 전송 오류 개인정보 비노출을 대상으로 한다.
