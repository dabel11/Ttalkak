# TTALKAK 최종 시연용 합성 입력 카드

> **시험 데이터**만 포함한다. 아래 행사·단체·일정은 모두 가상이고 실제 사업·회원·고객 정보가 아니다.
> 기대 결과는 **판정 기준**이지 이미 서버에서 확인된 결과가 아니다.
> 실제 LLM API 호출, 로그인 계정 생성·게시물 저장은 범위·비용 승인을 받은 다음 실행한다.

## A. 명확한 작업 + 주제 — 첫 턴 즉시 개선

**입력 (복붙)**

```text
가상의 '별빛도서관'에서 진행하는 청소년 독서모임 홍보 문구를 만들어줘.
대상은 중학생이고, 2026년 11월 12일 오후 2시에 도서관 A실에서 진행해.
문구는 3문장으로, 친근하지만 과장 없이 써줘.
참가비와 신청 링크는 아직 정해지지 않았어.
```

**검수 기준:** 작업(홍보 문구)과 주제(가상 독서모임)가 충분하므로 개선안이 첫 턴에서 제공되는지 확인. 날짜·장소·대상·문장 수는 유지한다. **참가비를 무료라고 단정하거나 신청 링크를 지어내면 실패.** 추가 질문이 표시되더라도 개선안을 바로 실행할 수 있어야 한다는 제품 설계 의도를 확인한다.

**증거:** 원본, 개선된 프롬프트, 질문 유무, 선택 실행 가능 여부, 실제 생성 결과에서 없는 사실을 추가했는지(사람 판단 필요).

## B. 정보 부족 — 질문을 우선

**입력 (복붙)**

```text
안내문 작성해줘.
```

**검수 기준:** 안내 대상/목적/주제가 없으므로 이를 임의로 특정하지 않고 필요한 내용을 질문하는지 확인. 실재 행사명·회사명 등을 창작해 단정하는 개선안은 실패로 본다.

**확인할 질문 예시:** “어떤 대상에게 무엇을 안내하려는 건가요?” 질문 문구 자체는 다를 수 있다.

## C. 다중 턴 — 이전 제약과 새로운 조건 유지

**첫 입력 (복붙)**

```text
가상 사내 스터디 모집 메일을 작성해줘.
대상은 신규 입사자, 주제는 업무 자동화 입문이고, 한눈에 읽히게 5줄 이내로 써줘.
모집 인원과 신청 방법은 정해지지 않았으니 넣지 마.
```

**후속 입력 (동일 대화에서 사용)**

```text
이번에는 조금 더 격식 있는 말투로 바꿔줘.
그리고 첫 문장에 스터디 목적이 명확하게 드러나게 해줘.
```

**검수 기준:** 후속 요청에서 **기존 대상·주제·길이·알 수 없는 인원/신청 방법을 넣지 말라는 조건**을 유지한 채 말투와 첫 문장만 개선했는지 확인한다. 새로운 날짜·인원·신청 링크를 만들어 넣으면 실패.

## D. 권한·저장 및 장애 대응 (사전 승인 후)

이 시나리오는 단순 복붙 프롬프트만으로 검증할 수 없다.

| 단계 | 기대 동작 | 검증 환경 |
| --- | --- | --- |
| 익명 이용 | 승인된 test fixture에서는 첫 3회 성공, 4회 제한 | `ttalkak-ci` 컨테이너 검증. 실서버는 별도 |
| 로그인 | A/B 계정마다 대화·폴더·저장 접근 분리 | 승인된 테스트 계정 |
| 저장→재로그인→재조회 | 저장한 프롬프트와 대화 이력 동일, 중복 요청 시 사용량 중복 집계 없음 | 승인된 테스트 계정·최소 비용 |
| 실패 응답 | API 지연/429/503에서 무한 재시도·중복 차감·개인 정보 노출 없음 | fixture 우선, 실공급자 시험은 별도 |
| 평가 | 원본 vs 개선안은 동일 target 모델로 실행, 사람 확인 | 기존 AI 담당자의 평가 도구 |

## 시연 시 주의사항

- 실험을 진행할 때 `PASS/FAIL/SKIP`와 실행 날짜/배포 커밋만 기록하고, 로그인 비밀번호·토큰·사용자 실데이터는 저장하지 않는다.
- Case A~C의 결과를 임의로 꾸며 발표하지 않는다. **실제 시연 전에 한 번이라도 검증을 완료한 케이스만** 본 발표에서 '동작'으로 표현한다.
- AI 결과가 기대와 다를 때는 누락/환각 유형을 실패 사례로 남겨 평가 자료에 넣는다.
- 서비스 장애 시 `GRADUATION_FINAL_DEMO.md`의 대체 발표 경로를 사용한다. 녹화 화면은 녹화 시각·버전을 표기하고 현재 실서비스 결과처럼 소개하지 않는다.
