## 2. P0 합격 기준 — 실제 기능 통합

검증 장소를 반드시 기록한다(`CI disposable`, `staging test account`, `real provider` 등).
실제 운영/공용 계정에 비용이나 게시물을 발생시키는 작업은 사전 합의한 테스트 계정과 호출 한도에서만 실시한다.

| ID | 시나리오 | 합격 기준 | 상태 |
| --- | --- | --- | --- |
| INT-01 | Web 정적 파일, `/healthz`, `/api/tags/popular`, `/api/auth/config` | HTTP/본문 규약 충족, 오류나 비밀값 노출 없음 | 공개 API 3개 실제 스테이징 200 확인; 전체 정적·브라우저 흐름은 미검증 |
| INT-02 | 비회원 프롬프트 개선 3회·4회·실패 재시도 | 성공 3회만 집계, 4회는 429, 공급자 실패는 미차감 | CI fixture 검증, 실배포 미검증 |
| INT-03 | 가입/로그인 → 개선 → 대화 이력 → 저장 → 재조회 | 사용자 의도·requestId·저장 결과 일치, 중복 요청 안전 | CI 일부 검증, 실배포 미검증 |
| INT-04 | 사용량·등급·기간 전환 | `/api/me/usage` 결과와 실제 기록 일치, 누락/중복 집계 차단 | 코드·CI 일부 검증, 실배포 미검증 |
| INT-05 | Google 로그인/메일 복구/세션 만료·해지 | 사용자 계정·인증 수단·오류 안내 일치 | 실제 공급자 E2E 미검증 |
| INT-06 | AI 서버 장애, 장시간 응답, 404/429/503 | 재시도·오류 메시지·요청 차감 정책 일치 | 실환경 최종 확인 필요 |
| INT-07 | 관리자·일반 사용자 권한 경계 | 비인가 401/403, 관리자 API 권한 외 접근 차단 | 실배포 비로그인 회원·관리자 GET 401 및 미허용 CORS 403 확인; 타 회원 간 권한/실제 관리자 로그인 검증 필요 |

자동 검증 예시(읽기 전용):
```bash
python3 scripts/check-staging-readiness.py --origin https://web-production-a82d94.up.railway.app
```
현재 `develop`에 병합된 검사기는 `--security`로 익명 접근 및 CORS 경계를 추가 검증한다. [PR #68](https://github.com/dabel11/Ttalkak/pull/68)의 수동 실행 가능한 Actions 워크플로로 실제 배포 사이트 점검을 반복할 수 있다. 인증된 점검에는 **명시적으로 승인된 테스트 계정**과 로컬 환경변수만 사용하고, 토큰·사용자 원문·복구 코드는 저장소나 이슈에 기록하지 않는다.

실제 LLM 요청은 금액을 발생시킬 수 있으며 읽기 전용 검사로 분류하지 않는다. 테스트 요청의 입력·예상 결과·실패 처리 기준을 사전 확정한다.

## 3. P0 데이터 보호 — 백업·복구 수락 기준

MySQL은 Railway의 `mysql-volume`에 보관되고 있지만 **영구 볼륨은 백업이 아니다**.

- [ ] 백업 방식·보관 주기·보관 위치·접근 권한을 확인(암호/접근 URL 공개 금지)
- [ ] 일관된 MySQL 백업본을 작성하고 생성시각·용량·DB 버전을 기록
- [ ] 운영 MySQL이 아닌 격리 DB 인스턴스/별도 볼륨에만 복원
- [ ] 핵심 테이블의 존재·행 수·참조 무결성·테스트 계정 접근 결과를 비교
- [ ] 복원 성공 여부, 담당자, 복구 소요시간(RTO 측정치)을 기록
- [ ] 운영 DB의 초기화·DROP·스키마 변경·볼륨 삭제 금지

운영 DB에 스키마 변경을 적용하기 전 `JPA_DDL_AUTO` 실제 설정을 점검한다. 코드는 기본값 `update`이므로 별도 마이그레이션 정책을 검토한다. 기존 DB에 미검증된 Flyway/Liquibase baseline을 바로 적용하지 않는다.

## 4. P0 AI 품질 평가 — 담당자 협업 기준

AI 담당자의 기존 평가 도구 및 코퍼스를 최대한 활용한다. 사용자 대화를 외부 공개 평가셋에 그대로 복사하지 않는다.

- [ ] **고정 평가셋**: 작업·주제 명확/모호/정보 부족/환각 유도/멀티턴/긴 입력을 포함하고 케이스 ID와 입력 버전 고정
- [ ] **품질 비교**: 원본과 개선 프롬프트를 동일한 실행 조건에서 비교, 평가 순서 교체로 위치 편향 완화
- [ ] **평가 항목**: 의도 보존, 지시 명확성·충실도, 없는 사실 생성 여부, 사용자 선택·추가 질문의 적절성
- [ ] **검색 지표**: 기존 Recall@k, nDCG@5, MRR 평가 도구 결과 활용
- [ ] **성능/비용**: 요청 성공률·p50/p90 응답시간·모델별 API/리랭커 사용량을 분리 기록
- [ ] **보고**: 표본수·평가모델·실행 조건·평가 기준·실패 사례·한계까지 보고. 성능 개선 수치 임의 기재 금지

## 8. 백엔드 보안·운영 안정화 통합 작업 (시험기간 검토 보류)

이 섹션은 `hardening/backend-graduation-batch` 작업 브랜치의 진행 기준이다. **CI를 통과하거나 `develop`에 반영되기 전에는 완료로 표시하지 않는다.** 팀원에게 개별 PR 리뷰를 반복 요청하지 않고 관련 변경을 한 묶음으로 정리한다.

| 범위 | 자동 검증 | 한계 및 후속 조치 |
| --- | --- | --- |
| Git 추적 민감파일 예방 | `scripts/check-tracked-sensitive-files.py`로 비공개 `.env`, 인증서/키 파일명 등을 차단하고 회귀 테스트 실행 | 파일명 검사만 제공. 파일 **내용·Git 과거 커밋·GitHub Actions 로그의 유출 여부는 별도 시크릿 스캔 및 검토 필요** |
| 소유권 API 경계 | 폐기 가능한 CI MySQL에서 다른 회원의 공개 게시글 수정·삭제·공개범위 변경에 403 응답 확인 | 운영 DB 및 실사용자 데이터 변경 없음. 다른 모든 객체/권한 조합에 대한 침투 테스트는 별도 |
| 인증 요청 제한 | 직접 요청한 필터에서는 위조 X-Forwarded-For 값으로 제한을 우회하지 못하는지 단위 검사 | Railway의 실제 프록시 클라이언트 IP 전달·다중 인스턴스 분산 제한 검증과 **동일한 검사가 아님**. 운영 전 게이트웨이 IP·제한 정책 검토 필요 |

### 후속 보안 검증 순서

1. 동일 스테이징에서 **서로 다른 테스트 회원 2개**로 객체 소유권·노출(게시글, 저장, 대화, 폴더, 관리자 API)을 확인한다. 계정·데이터 생성은 사용자 승인 후 최소 범위로 진행한다.
2. 저장소의 현재 내용 및 과거 커밋에 대한 고신뢰 시크릿 검사를 적용하고, 실제 비밀정보가 노출된 경우 키 교체·공개 히스토리 대응을 진행한다.
3. 인증 요청 제한의 실제 IP 기준, 다중 인스턴스, 로그인 복구·계정 열거, 로그 민감정보, 운영 CORS 설정을 검증한다.
4. 운영 MySQL(현재 Railway에서는 MySQL 9, CI에서는 MySQL 8.4)의 백업·복원 및 스키마 마이그레이션을 **격리 환경**에서 검증한다.
5. 라이브 자동결제·부분/업그레이드 환불·관리자 운영·개인정보 보존 및 삭제 정책은 졸업프로젝트 후 사업화 단계에서 별도 승인 후 진행한다.

> 비밀번호·API 키·JWT·실제 사용자 입력은 이슈/PR/채팅에 복사하지 않는다. 운영 변경은 PR 승인과 안전성 검증 전까지 수행하지 않는다.
